# Secrets: decisions

Decisions about how the app keeps and removes the owner's secrets (API keys, links) that the code alone does not explain. Newest last; each names the date and the pull request that settled it.

- **2026-10-30, #282: leftovers of the withdrawn calendar trips go at start-up, as far as the keychain allows.** The app removes `calendar/ical-link` and `geoapify/api-key` from the keychain and from `secrets.json` at each start (`CalendarLeftovers`). A copy in the keychain may stay until a start at which the keychain is usable and holds it: while the keychain is locked or unavailable, while `secrets.json` lacks the names but the keychain has them, or after the engine has postponed asking for the keychain. There is no retry within a session. A keychain that stays locked is the owner's to unlock; the app never asks for it unprompted.
- **2026-10-30, #282: removing a secret never asks to unlock the keychain.** Checked on a KDE desktop with KWallet through the Secret Service: no prompt. GNOME Keyring is not checked yet; it belongs to the GNOME check of #52.
- **2026-10-30, #282: the start-up clean-up is not described in the user docs.** Only builds of `main` between v0.5.0 and #282 wrote these secrets; no release did. The reason lives in the Javadoc of `CalendarLeftovers` and `ConfigFormat`.
- **2026-10-31, #268: a keychain without a locked state is never locked.** Such a store never reports `LOCKED`, and the app cannot unlock it (`unlock` refuses). On Android the Keystore key needs no authentication by the owner: it protects the secrets because it never leaves the device, so there is nothing to unlock.
- **2026-10-31, #268: every keychain gives back exactly what was written.** Any Unicode, quotes, line ends, an empty value (read back as empty, not as missing) and a long value (about 2 KB, below the Credential Manager's limit of 2560 bytes); there is no hard size limit. Names are the engine's own (`a-z`, `0-9`, `/`, `_`, `-`), and `index`, which lists the others, is kept like any other entry. `KeychainContractTest` checks this for every store.
- **2026-10-31, #268: three kinds of keychain failure, and no other exception.** Unavailable: the store cannot be used at all. Locked: only a store that can be locked, while it is. Refused: the store answered and failed, including a value it cannot decrypt. A store throws only a `KeychainException`, never a runtime exception, so the engine can always fall back.
- **2026-10-31, #268: a save sends the API keys to `secrets.json` on every failure but a locked keychain.** The engine waits for the owner only when the keychain is locked, or refuses an unlock, which `ApiKeys` counts as not answered, so the save ends locked. Any other failure of a save, unavailable or refused, writes the keys to the private file. A load whose first read of the `index` fails takes the file as their place; a failure later in a load, of an entry or from a damaged index, is reported as keys that could not be read, and the file is not used. This was so before #268 too; the contract now says it. As this does not keep the keys encrypted on Android, #273 makes the fallback a setting of `ApiKeys` that is off there.
