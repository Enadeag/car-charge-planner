# Secrets: decisions

Decisions about how the app keeps and removes the owner's secrets (API keys, links) that the code alone does not explain. Newest last; each names the date and the pull request that settled it.

- **2026-10-30, #282: leftovers of the withdrawn calendar trips go at start-up, as far as the keychain allows.** The app removes `calendar/ical-link` and `geoapify/api-key` from the keychain and from `secrets.json` at each start (`CalendarLeftovers`). A copy in the keychain may stay until a start at which the keychain is usable and holds it: while the keychain is locked or unavailable, while `secrets.json` lacks the names but the keychain has them, or after the engine has postponed asking for the keychain. There is no retry within a session. A keychain that stays locked is the owner's to unlock; the app never asks for it unprompted.
- **2026-10-30, #282: removing a secret never asks to unlock the keychain.** Checked on a KDE desktop with KWallet through the Secret Service: no prompt. GNOME Keyring is not checked yet; it belongs to the GNOME check of #52.
- **2026-10-30, #282: the start-up clean-up is not described in the user docs.** Only builds of `main` between v0.5.0 and #282 wrote these secrets; no release did. The reason lives in the Javadoc of `CalendarLeftovers` and `ConfigFormat`.
- **2026-10-31, #268: a keychain without a locked state is never locked.** Such a store never reports `LOCKED`, and the app cannot unlock it (`unlock` refuses). On Android the Keystore key needs no authentication by the owner: it protects the secrets because it never leaves the device, so there is nothing to unlock.
- **2026-10-31, #268: every keychain gives back exactly what was written.** Any Unicode, quotes, line ends, an empty value (read back as empty, not as missing) and a long value (about 2 KB, below the Credential Manager's limit of 2560 bytes); there is no hard size limit. Names are the engine's own (`a-z`, `0-9`, `/`, `_`, `-`), and `index`, which lists the others, is kept like any other entry. `KeychainContractTest` checks this for every store.
- **2026-10-31, #268: three kinds of keychain failure, and no other exception.** Unavailable: the store cannot be used at all. Locked: only a store that can be locked, while it is. Refused: the store answered and failed, including a value it cannot decrypt. A store throws only a `KeychainException`, never a runtime exception, so the engine can always fall back.
- **2026-10-31, #268: a save sends the API keys to `secrets.json` on every failure but a locked keychain.** The engine waits for the owner only when the keychain is locked, or refuses an unlock, which `ApiKeys` counts as not answered, so the save ends locked. Any other failure of a save, unavailable or refused, writes the keys to the private file. A load whose first read of the `index` fails takes the file as their place; a failure later in a load, of an entry or from a damaged index, is reported as keys that could not be read, and the file is not used. This was so before #268 too; the contract now says it. As this does not keep the keys encrypted on Android, #273 makes the fallback a setting of `ApiKeys` that is off there.
- **2026-11-01, #292: a save keeps the entries the keychain cannot read, and stores the rest.** When a save or the move from `secrets.json` reads an entry the keychain refuses (`REFUSED`, such as a value it can no longer decrypt), that entry stays in the keychain and in the `index`, untouched, and the other changes are saved; it no longer counts as "no keys stored", which made the save delete every other provider's entry. Entering a value for it replaces it; removing it deletes the entry and its name in the `index`. Writes go in the same order as before: the values, then the `index` with the kept names, then deleting the entries it no longer lists. Each such save logs one warning with the number and names (`forecast/<provider>/<name>`) of the entries kept unread, never a value. A locked keychain still wins over a refused entry (the owner is asked to unlock it), and an entry it cannot answer for (`UNAVAILABLE`) still sends the keys to the file. A damaged `index` (readable, but not a list of names) still counts as none, so a save starts a new one. There are no new texts: a successful save looks the same, and the next load still says the keys could not be read.
- **2026-11-01, #292: a save over an entry the keychain cannot read never falls back to `secrets.json`.** When the keychain holds such an entry and a write or delete of that save fails (a refused `index`, a refused delete of the entry the owner removed), the save fails and the owner is told the keys were not saved: the keychain was readable, and the file would hide the unreadable entry. What was written before the failure stays: a refused `index` leaves the old one, which still lists every entry; a refused delete leaves that entry in the keychain, no longer listed.
- **2026-11-01, #292: a refused `index` still sends the API keys to `secrets.json` (known behaviour).** The keychain is asked whether it can be used by reading the `index`, and a refused read of it counts as no usable keychain, as before. What it does on Android, where the fallback is off, is decided in #273.
- **2026-11-01, #292: removing a setting reaches an entry the keychain cannot read.** `ApiKeys.remove`, used at start-up for the leftovers of the calendar trips, checks the keychain's entries when a load fails on one it cannot read, so it removes such an entry (and its name in the `index`) and keeps it when removing another. Locked and file cases are as before.
- **2026-11-01, #292: a save never reads the `index` twice.** It deletes only entries listed in the `index` it read at the start of that save. A refused read of the `index` at that point sends the keys to `secrets.json`, as above, and leaves every entry; a damaged `index` still counts as none.
- **2026-11-01, #305: the fallback to `secrets.json` is a setting of `ApiKeys`, `KeyFallback`.** `PRIVATE_FILE` is today's behaviour, which the desktop keeps. With `NONE`, as on Android, the API keys never end up unencrypted: `secrets.json` is never read, written, deleted or moved, and `moveFileIntoKeychain` does nothing, so a file that is there anyway is left alone and ignored. A save the keychain cannot take (unavailable, or a refused write) fails as `FAILED`, which the desktop would show as "keys not saved"; a load from a keychain that cannot be used fails as keys that could not be read, instead of giving no keys, and keeps saying so until the keychain is asked again after `RETRY_AFTER`. The storage is then `KeyStorage.UNAVAILABLE`, never `FILE`. The desktop never sees `UNAVAILABLE`, so its texts for where the keys are kept refuse it rather than have a text of their own. A prompt to unlock that the owner dismisses saves nothing and ends as locked, as there is no file for the keys to go to.
- **2026-11-01, #305: without the fallback, a refused `index` counts as a damaged one.** A load says the keys could not be read, and a save starts a new `index` with only what it writes, so the owner can enter the keys again; the entries the old `index` listed stay as orphans until the same names are written again, as no save can find them. With `PRIVATE_FILE` a refused `index` still sends the keys to the file. A store used without the fallback therefore gives `REFUSED` only for what is lost for good, and `UNAVAILABLE` for a failure that may pass (#273).
