# Secrets: decisions

Decisions about how the app keeps and removes the owner's secrets (API keys, links) that the code alone does not explain. Each says what holds now and ends with the issue that settled it.

### Every keychain

- A keychain without a locked state is never locked: it never reports `LOCKED`, and the app cannot unlock it (`unlock` refuses). On Android the Keystore key needs no authentication by the owner: it protects the secrets because it never leaves the device, so there is nothing to unlock (#268).
- Every keychain gives back exactly what was written: any Unicode, quotes, line ends, an empty value (read back as empty, not as missing) and a long value (about 2 KB, below the Credential Manager's limit of 2560 bytes); there is no hard size limit. Names are the engine's own (`a-z`, `0-9`, `/`, `_`, `-`), and `index`, which lists the others, is kept like any other entry. `KeychainContractTest` checks this for every store (#268).
- A keychain fails in three kinds and no other. Unavailable: the store cannot be used at all. Locked: only a store that can be locked, while it is. Refused: the store answered and failed, including a value it cannot decrypt. A store throws only a `KeychainException`, never a runtime exception, so the engine can always fall back (#268).

### The fallback file, `secrets.json`

- Whether the API keys may fall back to `secrets.json` is a setting of `ApiKeys`, `KeyFallback`: `PRIVATE_FILE` on the desktop, `NONE` on Android (#305).
- With `PRIVATE_FILE`, a save waits for the owner only when the keychain is locked, or refuses an unlock, which `ApiKeys` counts as not answered, so the save ends locked. A prompt to unlock that the owner dismisses, and every other failure of a save, unavailable or refused, write the keys to the private file, except a save over an entry the keychain cannot read (below) (#268).
- With `PRIVATE_FILE`, a load whose first read of the `index` fails takes the file as the keys' place; a failure later in a load, of an entry or from a damaged index, is reported as keys that could not be read, and the file is not used (#268).
- The keychain is asked whether it can be used by reading the `index`; with `PRIVATE_FILE` a refused read of it counts as no usable keychain, so the keys go to `secrets.json` (#292).
- With `NONE` the API keys never end up unencrypted: `secrets.json` is never read, written, deleted or moved, and `moveFileIntoKeychain` does nothing, so a file that is there anyway is left alone and ignored (#305).
- With `NONE`, a save the keychain cannot take (unavailable, or a refused write) fails as `FAILED`, which the desktop would show as "keys not saved". A load from a keychain that cannot be used fails as keys that could not be read, instead of giving no keys, and keeps saying so until the keychain is asked again after `RETRY_AFTER`. The storage is then `KeyStorage.UNAVAILABLE`, never `FILE` (#305).
- The desktop never sees `UNAVAILABLE`, so its texts for where the keys are kept refuse it rather than have a text of their own (#305).
- With `NONE`, a prompt to unlock that the owner dismisses saves nothing and ends as locked, as there is no file for the keys to go to; a keychain that turns out to be gone when it is asked to unlock fails the save as `FAILED`, as one that cannot be used (#305).
- With `NONE`, a refused `index` counts as a damaged one: a load says the keys could not be read, and a save starts a new `index` with only what it writes, so the owner can enter the keys again. The entries the old `index` listed stay as orphans until the same names are written again, as no save can find them. A store used without the fallback therefore gives `REFUSED` only for what is lost for good, and `UNAVAILABLE` for a failure that may pass (#305).

### Saving and removing keys

- A save keeps the entries the keychain cannot read and stores the rest. When a save or the move from `secrets.json` reads an entry the keychain refuses (`REFUSED`, such as a value it can no longer decrypt), that entry stays in the keychain and in the `index`, untouched, and the other changes are saved; it does not count as "no keys stored", which would make the save delete every other provider's entry (#292).
- Entering a value for an unreadable entry replaces it; removing it deletes the entry and its name in the `index` (#292).
- A save writes in this order: the values, then the `index` with the kept names, then deleting the entries it no longer lists (#292).
- Each save that keeps unread entries logs one warning with their number and names (`forecast/<provider>/<name>`), never a value (#292).
- A locked keychain still wins over a refused entry (the owner is asked to unlock it), and, with `PRIVATE_FILE`, an entry the keychain cannot answer for (`UNAVAILABLE`) still sends the keys to the file; with `NONE` the save fails as `FAILED`. A damaged `index` (readable, but not a list of names) counts as none, so a save starts a new one (#292).
- Unreadable entries bring no new texts: a successful save looks the same, and the next load still says the keys could not be read (#292).
- A save over an entry the keychain cannot read never falls back to `secrets.json`: when a write or delete of that save fails (a refused `index`, a refused delete of the entry the owner removed), the save fails and the owner is told the keys were not saved, because the keychain was readable and the file would hide the unreadable entry. What was written before the failure stays: a refused `index` leaves the old one, which still lists every entry; a refused delete leaves that entry in the keychain, no longer listed (#292).
- A save never reads the `index` twice: it deletes only entries listed in the `index` it read at the start of that save. A refused read of the `index` at that point sends the keys to `secrets.json` with `PRIVATE_FILE` and leaves every entry; a damaged `index` counts as none (#292).
- `ApiKeys.remove` reaches an entry the keychain cannot read: when a load fails on one, it checks the keychain's entries, so it removes such an entry (and its name in the `index`) and keeps it when removing another (#292).

### The Android keychain

- On Android the API keys are kept in one encrypted file, `keychain.json` in `noBackupFilesDir`, with its keys in the Android Keystore. `EncryptedKeychain` encrypts each value with AES-256-GCM under a random 12-byte IV that the cipher picks, with the entry's name as additional authenticated data, so an entry moved to another name fails its check (#306).
- The file is `{"version": 1, "key": alias, "entries": {name: {"key": alias, "value": Base64 of IV and ciphertext}}}`, written whole and atomically through `PrivateFiles`: the file names the key that new values are encrypted with, and each entry the key it was encrypted with (#306).
- The first key is an AES-256 key under the alias `keychain`, made at the first write, without authentication by the owner and usable while the phone is locked, with randomized encryption and without StrongBox; a key never leaves the phone and cannot be read out. The store has no locked state (#306).
- The store's logic sits behind a seam for its keys (`KeychainKeys`), so the engine's `KeychainContractTest` runs on every pull request on the JVM with software keys, and an instrumented test runs it on the real Keystore (#306).
- The engine's other files (settings, trips, the forecast cache) are in `filesDir`, with `FilePrivacy.NONE`. `AndroidPlatform` makes these parts once per process, with `ApiKeys` under `KeyFallback.NONE`, and the keychain lets one call at a time reach its file, also through two instances (#306).
- The store answers `REFUSED` only for what is lost for good: an entry's key still missing after three looks within about a second; a key the Keystore has invalidated (`KeyPermanentlyInvalidatedException`) or, from Android 13 on, cannot load for a reason the Keystore does not call transient (`UnrecoverableKeyException` caused by a Keystore error whose `isTransientFailure()` is false), because a loss counted too readily costs only a new alias; an entry that fails its check (`AEADBadTagException`) or is not this format; a file that is not this format (on a read or a delete; an alias that is not `keychain` or `keychain-<n>` from 2 makes either one not this format); a file of a newer version; and a value UTF-8 cannot hold (#306).
- A file it cannot read or write, every other failure of the Keystore (an `UnrecoverableKeyException` before Android 13 among them, as it does not say why), an interrupt while looking again, and every runtime exception (such as `ProviderException`) are `UNAVAILABLE`, and nothing changes. `EncryptedKeychain`'s Javadoc lists each case (#306).
- Looking again for a missing key may hold a call for about a second, so the keychain is used off the main thread (#306).
- The store never removes a key or an entry. When the key in use is lost for good, or still missing after the looks while entries need it, the next write makes a new key under the next alias that no entry names and that holds no key (`keychain-2`, `keychain-3` and so on), and records it in `keychain.json`. The old key is never removed and its entries stay: readable again should the key come back, otherwise refused, encrypted orphans until their names are written again. Entries that a damaged `index` no longer lists stay as orphans too (#306).
- A file that is not this format is moved aside to `keychain.json.damaged` in the same folder (replacing an older one, in one step where the file system can) before the next write replaces it, so a damaged file can still be looked at, with one warning that names the paths only. A failure to move it fails the write as `UNAVAILABLE` and leaves the file in place. A file of a newer version is never overwritten or moved (#306).
- The data extraction rules (Android 12 and later) and the full backup rules (Android 10 and 11) exclude `no_backup/keychain.json`, its temporary file and the copy set aside as `keychain.json.damaged` from cloud backup and from device-to-device transfer, so the keys must be entered again on the owner's next phone; settings, trips and the cache move to it. `allowBackup` stays `false`. What else the rules exclude is in [android/notifications.md](../android/notifications.md) (#306).
