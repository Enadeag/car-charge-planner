# Android: build, tests and CI

Decisions about building, testing and checking the Android app: SDK levels, dependencies, the debug build, StrictMode, the tests, mutation testing, the licence files, the emulator job, R8, the release, dependency verification, and the icon and the listing for F-Droid.

What holds on every screen (top app bar, buttons, snackbars, dialogs, spoken names, saved state) is in [screens.md](screens.md); read it too.

### SDK levels and dependencies

- The app compiles against SDK 37, which resolves to `platforms;android-37.0`, with AGP's default build-tools (36.0.0) and no `buildToolsVersion`; targetSdk is 37 (#321, #383).
- The screen tests use Espresso 3.7.0, because the 3.5.0 that Compose's test rule brings calls `InputManager.getInstance()`, which Android 17 removed; the instrumented tests keep 3.5.0 while the emulator runs API 29 (#321).
- One test of the notifications card's refusal in `HomeScreenTest` runs on SDK 36, because Robolectric 4.17 counts the manifest's permissions as granted on 37; it is tried again with each Robolectric update (#321).
- Target 37, walked against Android's behaviour changes for apps targeting Android 17 and for all apps (#383):
  - The app has no widget or `RemoteViews`, reads no SMS or contacts, uses no Bluetooth and plays and records no audio, so those changes do not apply.
  - The app does not reflect on `MessageQueue` or change a `static final` field. Espresso 3.7.0 and Robolectric 4.17 meet the new queue's minimum, and the instrumented tests keep Espresso 3.5.0 on the API 29 emulator, where the old queue runs.
  - Native libraries are loaded by name with `System.loadLibrary` (by datastore-core and graphics-path), never with `System.load` from a file the app can write, so the read-only rule does not apply.
  - The manifest sets no orientation, resizability or aspect ratio, so ignoring them on large screens changes nothing.
  - The API key field already hides its text (`PasswordVisualTransformation`, shown only with Show), so the setting that hides passwords typed on a physical keyboard changes nothing.
  - `setContentCaptureEnabled` is never called, and Settings sets `FLAG_SECURE`, which is what Android 17 asks for to keep the screen out of content capture.
  - A notification opens the app through a `PendingIntent` to the app's own alias, started by the user's tap, and no code starts an activity from the background, so the stricter background activity start rules do not apply.
  - Certificate Transparency is on for every https host, because the configuration has no trust anchors of its own, and Encrypted Client Hello keeps Android's default; neither is opted out, and both show only on a device.
  - The release configuration names `localhost`, `127.0.0.1` and `::1` with plain http refused, because Android otherwise adds a configuration of its own that allows plain http to the device itself. Naming one such host already keeps Android's configuration out, so every other spelling (`ip6-localhost`, the rest of 127.0.0.0/8) falls to the base rule and is refused too; `NetworkSecurityConfigTest` pins the three names.
  - Settings refuses a server address with plain http as the release build's network security configuration does, in every build type, the debug build too (#509).
  - The permission for the local network (`ACCESS_LOCAL_NETWORK`) is not declared or asked, so a server on the owner's own network cannot be reached on Android 17 and later, as the privacy page says; whether to support it is #505.
  - The text-change types for typing Chinese, Japanese, Korean or Vietnamese on a physical keyboard are for `TextView`, and the app's fields are Compose.
  - Of the changes for all apps: the keyboard is not shown again after a rotation, as the activity is made anew and the app does not ask for it, which is accepted; the app holds one Keystore key, far under the new limit per app; it sends no `ACTION_SEND`, sets no `usesCleartextTraffic`, captures no pointer and sends nothing to its own device across profiles; the memory limit shows only on a device.
  - Checked on a phone with Android 17 (2026-11-19), with the release build of a dry run: set-up with the place search, the forecasts of both providers, refreshing, a rotation with the keyboard open, a notification and its tap, the hourly round after an hour and after a restart all worked, so Certificate Transparency and Encrypted Client Hello stand in the way of neither provider.
- Dependabot has no ignore entries for the AndroidX libraries: every update is a pull request behind CI and review (#321).
- `material-icons-core` is the only icon library; `NOTICE` names it as an exception, with its licence in `android/legal/apache-2.0.txt` (#315).
- DataStore brings a repackaged Protocol Buffers under BSD-3-Clause, whose text is `android/legal/protobuf.txt` (#361).

### Debug build and signing

- The debug build has `applicationIdSuffix = ".debug"`, so it can never update the released app, the launcher label "Car charge planner (debug)", and the version name suffix `-debug+<first 7 characters of the commit>` on CI (`BUILD_COMMIT`), `-debug+dev` elsewhere (#355).
- It is signed with `android/app/debug.keystore`, a public key (alias `androiddebugkey`, password `android`), marked binary in `.gitattributes` (#355).
- `checkReleaseNotDebugSigned`, under `check`, fails when any build type other than debug, by its effective signing config (its own, a product flavour's, or the default config's), is signed with the debug key or a copy of it (#355).
- CI uploads only `app-debug.apk`, as `android-debug-apk-<run number>-<run attempt>`, for 14 days, also when lint or the tests failed; not for a pull request from a fork or by Dependabot. The job has `contents: read` and posts no comment on the pull request (#355).

### StrictMode

- The debug build detects disk reads, disk writes and network on the main thread, set in `onCreate` after the engine is built; the release build sets no policy, and there is no VM policy (#347).
- A violation crashes the app only when a frame of its stack is in `nl.enadeag.carchargeplanner.`, because a phone's own input code read a file on the main thread; the crash is an `IllegalStateException` posted to the main looper right after the current message, never thrown inside StrictMode or a vendor's code (#347).
- Other violations are logged at warn, once per kind and stack, up to 32, then one line says further ones are not logged. Vendor code running inside one of the app's lambdas still crashes (#347).
- The parts that ask for the app's folders are made in `onCreate` with the disk policy lifted around them (`beforeThePolicy`), because Robolectric runs each test's application on a main thread where an earlier test set the policy already (#382).

### Tests

- Screen tests run on Robolectric only, with explicit checks (name, role, a drawn size of 48 dp, scrolling at font scale 2) in place of Compose's accessibility checks, which find nothing there. What TalkBack says is checked on a phone before a release, by the list in `docs/accessibility.md` (#314).
- `AppArchitectureTest` holds the app to ADR 0005's wiring rules (one clock, no static mutable state but `EncryptedKeychain.LOCKS`, threads only from the root, `AndroidPlatform` no singleton), with rules on cycles, screens, engine access and sleeping in tests (#382). The engine's classes are not among the app's: `EngineArchitectureTest` holds them to theirs, and the engine's files take the clock the app hands in, so no exception for a clock is left (#285).
- The home screen stays split into a file per card (#382).
- `check` packages the debug APK, for `LicencesInTheApkTest` (#331).

### Mutation testing and coverage

- PIT runs on `:app` through `pl.droidsonroids.pitest`, with PIT's versions taken from `pom.xml`, so Maven and Gradle run the same PIT; Dependabot updates only the plugin (#327).
- It mutates the app's logic (`pitLogic`), the debug variant only; the screens' Robolectric tests and the tests of resources, manifest, APK and architecture are left out by name, and the screens keep hand mutants in review (#327).
- `./gradlew :app:pitestDebug` runs it, `-PpitClasses=…` on the changed classes only; an empty `-PpitClasses` fails, and a narrowed run has no floor (#327).
- `checkPitScore` leaves out the Kotlin compiler's own null and result checks, which no test can kill, and holds the full run to 84% (#382).
- PIT's test classpath gets test-only artifacts for Android's mockable jar, never the APK; their known CVEs do not apply, and `excludeMockableAndroidJar = true` breaks PIT's coverage (#327).
- `mutation.yml`'s `android` job runs weekly and by hand only, never on a pull request (#327).
- `checkCoverage`, under `check`, holds JaCoCo's line and branch floors, the screens included (#382).

### Licence files in the APK

- The hand-kept files in `android/legal` are the source; `licenceAssets` copies them with `NOTICE`, `LICENSE` and `ADDITIONAL-TERMS.md` into the assets, the same bytes on every machine, without a licence plugin (#331).
- `checkLegalFiles` holds those files to the release build's libraries by `group:artifact`, to the jars' `META-INF/NOTICE*` texts (line endings, trailing spaces and blank end lines ignored), and to third-party files in the app's `src` and the engine's `src/main`. A symbolic link, or anything but plain UTF-8 `.txt` in `android/legal`, fails the build (#331).
- Only modules that bring a file get an `Artifact:` line; KMP root modules and BOMs get none (#331).
- The GPLv2 §3 source of `desugar_jdk_libs_nio` is offered by pointing at its upstream commit, as the desktop does for OpenJDK (#331).

### Emulator job

- The instrumented tests boot a new AVD cold each run (`force-avd-creation: true`, `-no-snapshot`), without an AVD cache, because boots from a cached snapshot sometimes lacked the `input` service and failed the action's own keyevent (#371).
- The script first waits about 60 seconds for the services `input`, `settings`, `package` and `activity` (`adb shell service check`, each limited to 5 seconds, 1 second between rounds), logs "services ready after N s", and on a timeout fails, printing the missing services, `adb devices` and the last 100 lines of logcat, each limited to 10 seconds. A step before logs the runner's CPU model (#371).
- A step before the emulator's builds the debug build, the minified build and both test APKs, so the emulator step only installs and runs them; it has `timeout-minutes: 15`, for the boot and the tests, and no `continue-on-error`, so a hang on shutdown fails the job fast (#371, #485).
- After the debug build's tests, a second Gradle call in the same boot runs the minified suite (see [R8](#r8)), with a key a step before made for the run (its password in `MINIFIED_KEYSTORE_PASSWORD`, never the release key's variable), so `android-release.yml`'s gate on the emulator job covers it without a change (#485).
- Then `tools/android-backup-check.sh` installs the debug build, puts made-up files where the backup rules name them (and a few they leave out), starts the app, backs it up with the local transport and fails unless the transport declined the backup as empty. The local transport sets the device-to-device flag only from Android 12, so this is the half of the transfer API 29 can show: a backup whose transport sets no flag saves nothing of the app; that a transfer with the flag moves the files it does not show. There is no positive control, a second app whose files the same backup saves: the AOSP image has no app that reliably holds files and allows a full backup, and a second build of the app with wrong rules would cost a build. What stands in for it: "Transport rejected package" comes only from the local transport's check of the size the app's backup agent measured (zero bytes; an agent that did not run gives "Agent error"), and `DataExtractionRulesTest` (`beforeAndroid12EveryRule…`) fails on an include without the flag; by hand, the script failed with such an include on API 28 and with a cloud-backup exclude removed on API 36. The debug build, because `run-as` needs a debuggable app; its manifest and rules are the release build's. The emulator's backup switch, transport and its settings are put back after it, also when the script is stopped (#397).

### R8

- The release build is shrunk by R8 (`isMinifyEnabled = true`) in AGP's default full mode without a compat switch, but not optimised (`-dontoptimize`, decided 2026-11-18): R8 cannot keep the source lines while it optimises, and the log is to show the real file and line without a mapping file. The APK is 9.4 MB, against 5.0 MB optimised and 30.1 MB unshrunk (#485).
- `proguard-android-optimize.txt` stays the default file only because AGP 9.5 refuses `proguard-android.txt`; the app's `proguard-rules.pro` switches optimising off (#485).
- R8 renames nothing (`-dontobfuscate`), so the log's tags, its stack traces' classes, methods, files and lines and the error texts that name a class stay readable without a mapping file; no `mapping.txt` goes with a release (#485).
- `-keepattributes SourceFile,LineNumberTable` keeps the real file names and lines; without it a frame names `SourceFile`. Optimising, R8 would name every file `r8-map-id-<id>` and number the lines anew whatever the rules say (#485).
- Resources are not shrunk (`isShrinkResources = false`), and stay so until #503 decides whether to shrink them: the change stayed with the code (#485). The minified suite finds the app's texts by resource name (`getIdentifier`), which resource shrinking can remove, so shrinking resources needs a look at the suite too; until #503 decides, `checkReleaseShrunk` fails when the release build shrinks resources (#485, #503).
- The keep rules are as narrow as possible: the libraries' own consumer rules first, then only what the build or the minified suite needs, each rule saying which. `-dontobfuscate`, `-dontoptimize` and `-keepattributes SourceFile,LineNumberTable` are held by `checkReleaseShrunk` and the suite; two named `-dontwarn` for the `java.beans` annotations Jackson looks for and does without, without which R8 fails the build. `LogcatServiceProvider` has no `-keep` (decided 2026-11-18): R8 keeps it and its no-argument constructor through `META-INF/services`, the suite passes without the rule, and the rules file holds only rules something fails without; the suite's logger test, which every release passes in the emulator job, fails if a later R8 or slf4j changes that, and the rule comes back with that proof. No `-keep` of all of Jackson, no `-dontwarn **`, no absolute path and no `-printconfiguration`, for #424 (#485).
- The debug build stays unshrunk, as Robolectric, coverage and PIT run on it (#485).
- `checkReleaseShrunk` (in `android/build-logic`, under `check` and before every build of a type other than debug) fails when the release build is not minified, shrinks resources, a rule file of its own says `-dontshrink`, or none says `-dontobfuscate`, `-dontoptimize` or `-keepattributes` with `SourceFile` and `LineNumberTable`: a tripwire against a mistake, not intent (#485).
- The build type `minified` is the release build (`initWith`) with an id of its own (`.minified`), signed by Gradle with a key made for the run (`tools/android-sign.sh throwaway-key`, named by `-PminifiedKeystore`, its password in `MINIFIED_KEYSTORE_PASSWORD`, which the build reads only when `-PminifiedKeystore` is given and then needs, failing with a message that names it when it is unset, so the release key's `ANDROID_KEYSTORE_PASSWORD` of a shell never reaches the configuration cache), never the debug key and never a committed one, so a device can run tests on it; `release` stays unsigned (#485).
- `-PtestBuildType=minified` makes it the tested build type for one Gradle call, debug staying the default; AGP and the configuration cache take the property (#485).
- AGP does not keep what the test APK refers to: the minified build's R8 configuration and list of removed code are those of the release build, also with tests that name app classes. The test APK leaves out every library the app has, so the tests run against the app's shrunk copies, which keep only what the app uses: a test that called the app's or a library's code could fail where the app does not (#485).
- So the minified suite (`src/androidTestMinified/`, Java) reaches the app only from outside, as Android and slf4j do: the logger by slf4j, the activity by intent on a prepared settings file and forecast, the plan by the accessibility tree, a round on WorkManager by WorkManager's own Logcat line, an API key saved through Settings by the accessibility tree. It runs on a runner of its own on JUnit 4 alone, as AndroidX Test's runner needs parts of Kotlin's library and `androidx.tracing` that R8 removes from the app, such as `kotlin.LazyKt`, also without optimising (#485).
- The logger's frame is checked against the logger's source, which the build puts in the minified test APK's assets: the file is `LogcatLogger.java` and its line is the one that writes the trace, so an edit of the logger moves nothing in the test (#485).
- The Keystore is tested through the app itself (decided 2026-11-18), as the suite touches the app only from outside: it types a made-up API key into Settings, Forecast and saves it, checks the keychain's file names the entry without the key, that the Android Keystore holds a key, that the key shows again after the activity is made anew and that it is not in the app's Logcat lines. It runs in the `.minified` installation, so the app's own alias there is no one's real key. The key shown again comes from the engine's memory of the save, as only a new process makes the app decrypt it anew, and one test run is one process (#485).
- The debug build's instrumented tests moved to `src/androidTestDebug/`, so the minified test APK holds none of their references (#485).
- `checkInstrumentedResults` (in `android/build-logic`) follows the connected test task, of the debug suite and of the minified one alike, and fails on a failure or on no test at all in its results: AGP 9.5 lets the task pass when the app's process crashes before the first test, as one without the App Startup rules did. For the minified suite it also fails when a class under `src/androidTestMinified/` with a test is not named in `MinifiedTestRunner`'s suite, which would never run it; a lost test or a death mid-run AGP itself reports, by the count of tests the runner announces (#485).
- Each rule was taken out in turn and the suite run; the pull request of #485 records what failed (#485).

### Release

How a release is built, signed and published (`android-release.yml`, `tools/android-sign.sh`; the steps are in [Releasing the Android app](../../dev/ci-and-releasing.md#releasing-the-android-app)). The release key and the environment are the maintainer's (#271); R8 is under [R8](#r8) (#485), the second build that must give the same APK under [Reproducible build](#reproducible-build) (#424); Gradle's dependency verification is under [Dependency verification](#dependency-verification) (#484).

- The release commit sets `versionName` in `android/app/build.gradle.kts`, and a tag that is not `android-v` plus that version, or a version that still ends in `-SNAPSHOT`, stops the run, so the tag, the APK and the notes can never disagree (#272).
- `versionCode` is major × 10000 + minor × 100 + patch (0.1.0 is 100), worked out only in `AppVersion` with its tests; a minor or patch above 99, any other form of the name and a code of 0 or above Play's 2,100,000,000 fail the build, as two versions could otherwise share a code (#272).
- Tags are `android-vX.Y.Z` only, without pre-releases; any other tag stops before the key is asked for (#272).
- Each job touches only what it needs, so the key never meets Gradle's plugins and the write token never meets the key (#272):
  - prepare (the tag's form, the version, the notes), build (lint, the tests, the unsigned APK) and reproduce (the same build again, compared; see [Reproducible build](#reproducible-build)) run Gradle with a read-only token and no secrets;
  - tag-checks and no-release-yet check out nothing and only ask GitHub's API; no-release-yet has `contents: write`, as GitHub lists draft releases only to a token that can write, the one exception to "only the release job writes";
  - sign has the environment `android-release` and runs `apksigner` through `tools/android-sign.sh`, no Gradle and no third-party action, with a read-only token; sign-dry-run does the same with a throw-away key and without the environment;
  - release has the token that writes the draft and the attestation, and no key.
- Before signing, the sign job checks the APK's SHA-256 against the build job's, that it is unsigned and zip-aligned, and its app ID, `versionName` and `versionCode`, so it signs only what the build made (#272).
- The sign jobs check out the repository again and stop unless it is at the commit the prepare job named, so the script and the fingerprint file are those of the commit that was built; the release job stops, before it makes the draft, unless the notes name the certificate of the APK that was signed (#272).
- Only the APK Signature Schemes v2 and v3, with exactly one signer, checked after signing: the app needs Android 10, which reads v3, so v1 would add nothing but files in the APK (#272).
- The certificate's SHA-256 fingerprint is recorded in `android/release-certificate.sha256`; a tag run refuses any other certificate, the debug one too, and stops early while the file records none (#272).
- The keystore reaches the runner only in the signing step's `env:`, is written to the runner's temp folder owner-only (`umask 077`), its password is passed to `apksigner` through `--ks-pass env:`, and it is removed in a step that always runs; the sign job uses no third-party action (#272).
- After signing the APK is read back: app ID without `.debug`, the tag's version, not debuggable, not test-only (#272).
- The signed APK's run artifact is kept for one day (`retention-days: 1`), as any signed-in user can download it until the draft is published or deleted; a rejected draft is deleted together with its workflow run, which removes the artifact (#272).
- A dry run skips the checks that need a tag (the tag's form, the release branch, the emulator job and an existing release) and only warns when `CHANGELOG.md` has no section for the version (#272).
- The sign jobs use the runner's own Java and install build-tools 36.0.0 with `sdkmanager`; the exact Java version is the build's, which `AndroidReleaseWorkflowTest` keeps (#272).
- "The emulator job was green" means a run of `android.yml` for the tag's commit, by push or by hand, whose `android-emulator` job succeeded (#272).
- The keystore is PKCS12 with one password for the store and the key, so `apksigner` takes the one secret for both (#272).
- The workflow only makes a draft, created with `--latest=false`; the maintainer reads and publishes it, and unticks GitHub's **Set as the latest release** when publishing, as `--latest=false` holds for the draft only (#272).
- The notes come from a changelog section `## [Android X.Y.Z] - date`, through `ReleaseNotes.java --android`, with an installing text of the APK's own; the desktop's notes stay as they were (#272).
- The dry run, started by hand, signs with a throw-away key made in the run in a job without the environment, so it never asks for the release key; it skips only the recorded certificate of the signing checks, and its draft, tag and APK name say "dry run" (#272).
- `release/android-X.Y.Z` must exist at the tag's commit before the key is asked for; the workflow never creates or moves it (#272).
- The signed APK gets a build provenance attestation, except in a dry run (#272).
- The files are `car-charge-planner-android-X.Y.Z.apk` and `SHA256SUMS`, as the desktop's, and the release's title is "Car charge planner for Android X.Y.Z" (#272).
- The build job runs lint, the unit tests and the build's checks again; it runs no emulator, but the run stops unless `android.yml`'s emulator job was green for the tag's commit in a push or a run by hand, as a pull request's run tests a merge commit (#272).
- One exact Temurin 21 (`AndroidReleaseWorkflowTest`) and build-tools 36.0.0 build the release; a Java update is a pull request (#272).
- A release, draft or published, that exists for the tag stops the run; nothing is overwritten. Runs for one tag wait for each other in order and are never cancelled (`queue: max`), up to GitHub's limit of 100 waiting runs in a group, beyond which a run is cancelled (#272).
- No cache anywhere in the workflow (`setup-gradle` with `cache-disabled: true`, no `actions/cache`, no `cache:` of `setup-java`), so no other run can change what is built or signed (#272).
- `AndroidReleaseWorkflowTest` holds the workflow's text to these rules, in the Maven build, so every pull request that changes the workflow runs it (#272).
- No check that the tag is reachable from `main`, as on the desktop: a release branch may carry a fix (#272).

### Reproducible build

Two builds of the same commit must give the same APK apart from the signature, and every release checks it before the key is asked for (#424).

- The job `reproduce` of `android-release.yml` builds the commit again on a runner of its own, with the build job's Gradle call, and compares its unsigned APK with the build job's by `cmp`, after checking that the build job's APK it downloaded has the SHA-256 the build job reported, the one `sign` checks too, so the APK compared is the APK that is signed and not another file under its name; `sign` and `sign-dry-run` wait for it, so a difference stops the release before signing (#424).
- What differs between the two builds: the runner, the checkout's folder, the Gradle home (a fresh one under the runner's temp folder) and the time zone and locale (`Pacific/Auckland` and `tr_TR.UTF-8`, against UTC and the runner's English), set only on the Gradle step and the step that checks the locale, so the checkout, `sdkmanager` and `locale-gen` keep the runner's own and only the build is put to the test; that step fails when Java does not see the Turkish locale, so the difference cannot silently fall away, and shows the time zone without checking it (#424).
- What is the same: the commit, the exact Temurin 21, the Gradle wrapper, `platforms;android-37.0` and build-tools 36.0.0, installed by the same steps without a cache (#424).
- Both jobs record the revisions of the build-tools and the platform and Java's version, and `reproduce` shows both beside the comparison, with a warning when they differ or one is missing, inside a block where their text cannot give workflow commands; only the APKs decide (#424).
- Where a release's versions are found: the tag's `android-release.yml` names the exact Temurin and build-tools 36.0.0, but only `platforms;android-37.0`, without its revision; that revision is in the run's log, as long as GitHub keeps it, and in the artifact `android-build-versions`, for 14 days. A later rebuild may therefore not learn the platform's revision, nor get an older one from `sdkmanager`, which installs the newest (#424).
- On a difference the job keeps both APKs and their `unzip -v` listings as the artifact `android-reproduce-difference-<run>-<attempt>`, for 14 days. It keeps no lint or test reports: the build job ran the same checks on the same commit and keeps its own, and a check that fails only here shows in the job's log (#424).
- It runs on a tag and in the dry run only, not weekly and not for pull requests: a change that breaks it shows at the next release, which waits until it is solved (decided 2026-11-18; #424).
- `tools/android-sign.sh` signs with `--alignment-preserved true`: `apksigner` from build-tools 35 on otherwise pads the entries anew (its own extra field `0xd935`, native libraries to 16 KB), so the signed APK's entries no longer sit where the unsigned build put them and the signature cannot be copied onto a rebuilt APK, as F-Droid does. The build stays on build-tools 36.0.0 (#424).
- The APK holds native libraries (`libandroidx.graphics.path.so` and `libdatastore_shared_counter.so`, for four ABIs), stored uncompressed and already aligned to 16 KB by AGP, with `classes*.dex`, `resources.arsc`, the baseline profile and the 9-patch images among the 29 stored entries; the option keeps that alignment, and `zipalign -c -P 16 4` still holds after signing (#424).
- The second build runs after the build job, so a release takes about one build job longer: in the first dry run the build job took 10 minutes and `reproduce` 11.5 (#424).
- The trial, by hand, with a throw-away key (2026-11-18): the unsigned release APK built with `./gradlew --no-daemon --max-workers=2 --console=plain assembleRelease` (and `--rerun-tasks clean assembleRelease` for the variants), not the release's `lint check assembleRelease`, in two folders of one machine with a local Temurin 21.0.7+6 (the release uses 21.0.13+9), build-tools 36.0.0 and platform 37.0 revision 2, was identical by `cmp`, also with `TZ=Pacific/Auckland`, with `tr_TR.UTF-8`, with `C` and with an empty Gradle home. One was signed by the script; `apksigcopier compare --unsigned` (apksigcopier 1.1.1, `apksigner` 36.0.0) copied its signature onto the other and the result verified, byte for byte the signed APK. Signed without the option, 59 of the 161 entries moved and the copied signature failed: "CHUNKED_SHA256 digest mismatch" (#424).
- The first dry run on `main` (2026-11-18, run 44392339199, commit 0fb925af) showed two runners giving the same APK, which the trial on one machine could not: `reproduce` found its unsigned APK byte for byte the build job's (SHA-256 `5897fead4a4ba7f16c5a9d5dc223aac60aa4b08c8ffc61242552cefc1b3637ad`), built with the release's `lint check assembleRelease` while Java saw the Turkish locale and New Zealand's time, both builds with build-tools 36.0.0, platform 37.0 revision 2 and Temurin 21.0.13+9; `sign-dry-run` started only after it. The run's result is recorded in #424, as GitHub keeps the log only for a time (#424).
- Not shown: that the APK does not depend on the JDK's vendor, as both builds use Temurin (#424).
- Not shown: that F-Droid's build gives the same APK, as F-Droid builds with a JDK and build-tools of its own; only its recipe running shows that, and the recipe and the request stay with #280 (#424).

### Dependency verification

Every file Gradle downloads is checked against its SHA-256 in `android/gradle/verification-metadata.xml`, so the signed release holds only recorded files ([Dependency verification](../../dev/android.md#dependency-verification); #484).

- Checksums only, SHA-256, with poms and `.module` files checked too (`verify-metadata`) and no PGP signatures or keyring (`verify-signatures` off) (#484).
- One file, for the root build, its plugins, `build-logic` and `maven-poms`, as Gradle reads only the file of the build it runs; `MavenVersionsTest`'s TestKit builds have none, as they download nothing (#484).
- Only `*-sources.jar` and `*-javadoc.jar` are trusted without a checksum, for an IDE, as the build never uses them; nothing else is trusted by a pattern (#484).
- Strict, Gradle's default, in every job (build, emulator, release, weekly mutation run); `AndroidDependencyVerificationTest` is a tripwire beside it, which Gradle's strict default does not depend on. It checks the settings of this file below; that no build script, source, properties file or wrapper script of the Android build names the mode's property or the API that sets the mode or switches it off; that the wrapper is the recorded one; that the repository's root and `release/` hold no `gradlew` or `settings.gradle(.kts)`, as a build there would run without this file; and, as plain text line by line, that no workflow or composite action under `.github/` gives Gradle `--dependency-verification` or `-F`, the property `org.gradle.dependency.verification`, `--write-verification-metadata` or `-M`, `--refresh-keys` or `--export-keys` (#484).
- `tools/refresh-android-verification.sh` is the one place with the list of tasks (those of CI, the release and the weekly mutation run, `assembleRelease` included, and the input files of the emulator job's `connectedDebugAndroidTest`, resolved without a device), and writes the file incrementally; its diff is read. It runs Gradle with an empty Gradle user home of its own, as Gradle leaves out parent poms and BOMs it has cached (gradle/gradle#19228), so the file holds what a fresh machine downloads. PIT runs narrowed to one class there, as its classpath is the full run's and the full run takes far longer. `--clean` rebuilds it from its header and configuration now and then, with the old file kept to compare; it fails and puts the old file back when a recorded file has another checksum, which a folded diff would hardly show (#484).
- Every task a `./gradlew` call of a workflow names belongs in the script's list, as the release and the weekly mutation run never run on a pull request; `:app:connectedTestInputs` stands for `connectedDebugAndroidTest`, and in a second Gradle call with `-PtestBuildType=minified`, beside `:app:assembleMinified` and `:app:assembleMinifiedAndroidTest`, for `connectedMinifiedAndroidTest` (#485). The review of a workflow change checks it (#484).
- Linux entries only, as CI builds on Linux; a Windows or macOS build fails on its own files, and such a developer runs the script on their own system (#484).
- Dependabot's pull requests for `/android`, and a version that reaches the build through `pom.xml`, are refreshed by hand: a step of `android.yml` says how after a verification failure, known by the report folder Gradle writes only then, and no workflow gets write rights (#484).
- Robolectric's `android-all-instrumented` jars come through a Gradle configuration per SDK the tests use, and the tests and PIT run Robolectric offline on them; `RobolectricSdkJarsTest` holds the jars to the Robolectric version, and Dependabot leaves them to a Robolectric update, as a lone bump would only fail that test (#484).
- The test is a tripwire against a mistake, not a guard against intent (decided 2026-11-18; #484). It had grown into a YAML parser with allowlists of Gradle calls, actions, inputs, variables and shell rules, and each round of review found a new way around it. A shell step can do anything, and whoever may edit a workflow may edit the test too, so that work could not be finished.
- Its limit: it catches a mistake, not intent. A workflow can switch the check off in ways the test does not see, such as a script it runs or a variable it builds. The review of a pull request that touches `.github/`, the Android build's files or the test is what protects against that (decided 2026-11-18; #484).
- The Android build's sources are read for the mode's property and API: Gradle and Kotlin scripts (`.gradle`, any `.kts`), Java, Kotlin and Groovy sources, every properties file and the wrapper scripts; a source folder named `build` is read, and only a `build` folder beside a build or settings script and outside `src` is skipped as output (#484).
- The wrapper is pinned: the SHA-256 of `gradlew` and `gradlew.bat`, with every line end read as LF, as the Windows job and a local checkout may have other line ends, and of `gradle-wrapper.jar` as it is; a Gradle update records the new values. The wrapper downloads Gradle from `services.gradle.org` with a recorded checksum into Gradle's user home (`distributionBase` and `zipStoreBase` `GRADLE_USER_HOME`, the paths `wrapper/dists`), as its scripts and jar run before Gradle reads any setting (decided 2026-11-17; #484).
- The short flags `-F` and `-M` count only on a line that names Gradle, a backslash's continuation joined, so `grep -F` or `tar -xf` elsewhere is no alarm. The hint after a failed check may name the refresh script and the metadata file, as the patterns are the flags, not those names (decided 2026-11-18; #484).
- The comparison of `--clean` was tried only with bash as `sh`, a known limit (decided 2026-11-17; #484).
- The cache of `android.yml` stays, as cached files are checked too; the release keeps building without a cache (#484).
- Outside the check, and not closed here: the Gradle distribution (the wrapper's `distributionSha256Sum`), the Android SDK and build-tools (`sdkmanager`, over HTTPS) and the JDK (`setup-java`, over HTTPS) (#484).
- The file is marked as generated in `.gitattributes` (#484).

### Icon and listing

The app's icon and its listing for F-Droid ([The listing for F-Droid](../../dev/android.md#the-listing-for-f-droid); #486).

- The icon is a white car under a yellow half sun on green (#1E8E5A). It is drawn inside the adaptive icon's 66 dp safe zone, so no launcher's mask cuts it, except the cap of the sun's top ray, which reaches about 1.2 dp beyond it (#486).
- The car carries the meaning: white on the green has a contrast of 4.1:1, the sun's yellow (#FFC940) only 2.7:1, under 3:1, so the sun is decoration (#486).
- The car's windows and wheel arches are holes in one path (`evenOdd`), not shapes in the background's green, so the themed icon of Android 13 and later, `ic_launcher_monochrome` with the same shapes in one colour, sun included, shows them (#486).
- The app needs Android 10, which takes the adaptive icon from `mipmap-anydpi`, so there are no round icon and no bitmap icons per density (#486).
- `tools/android-listing/icon.svg` is the one drawing: the vector drawables carry its path data, and the feature graphic takes its car and sun, so the launcher, the notifications and the listing show the same picture (#486).
- The notifications' small icon is the same car and sun scaled to 24 dp in one colour, as it follows the launcher icon (#361, #486).
- The listing is at the repository's root, `fastlane/metadata/android/`, one of the places F-Droid's page names, in `en-US` and `nl-NL`, the app's two languages; whether F-Droid finds it there with the recipe's subfolder shows when the recipe runs (#280, #486).
- It has no `icon.png`: F-Droid takes the icon from the APK, so there is no second copy to keep the same (#486).
- The texts are plain text, without the few HTML tags F-Droid allows, so they read the same wherever F-Droid shows them; they do not say the app works offline, as it needs the forecast (#486).
- The feature graphic has the car and sun and the app's name only, no words to translate; the same file is in both languages, as F-Droid's page calls `en-US` the fallback language but does not say that pictures fall back (#486).
- Each Android release adds its changelog in both languages in the release pull request (#486).
- `AndroidListingTest` checks F-Droid's limits, that the texts are plain text, the changelogs' names against the version code, that both languages hold the same changelogs and the same phone screenshots, numbered from 1 without a gap, and that every picture is a PNG of its size without text or time chunks (#486).
- Five phone screenshots per language, in the light theme at 1080x2400 with gesture navigation and a status bar cleaned by SystemUI's demo mode: today's dashboard with a charge window and the chart, a day with a trip and its advice, a grey day without a charge window, set-up's Welcome page, which says what leaves the phone, and Settings' Location page. Not the Forecast page, which refuses screenshots (#486).
- The pictures are made from an emulator by `tools/android-listing-pictures.sh`, so they can be made again when a screen changes; it does not run in CI, as a person looks at each picture before it is committed (#486).
- They show the made-up example home and a made-up forecast, never a live one: a stand-in for Open-Meteo on `127.0.0.1`, which the debug build may reach over plain http, answers relative to a fixed day, so the pictures come out the same on every run; nothing of a real owner, place or car brand is in them (#486).
- They show the app as a release does: the debug build, which `run-as` and the stand-in need, is built for them with `-PdebugAppName`, a Gradle property that only replaces its shown name, so no picture says "(debug)" and every other build stays as it was (#486).
- The Welcome page is taken on the app without any of its files, as at its first start; it needs no network (#486).
- The Location page is Settings', not set-up's: set-up's needs a place chosen from the search, which asks Open-Meteo's real geocoding service at an address the app does not let a setting change (`OpenMeteoPlaces`); Settings' Location page is the same page, with the example's place (#486).
- Dutch has its own set, with the emulator's language set to Dutch and the same data and clock, and the place named as the search names it in Dutch; the app's name stays "Car charge planner", as in the app (#486).
