# Engine: decisions

Decisions about the engine that both apps share, the desktop app and the Android app, that the code alone does not explain. Newest last; each names the date and the issue or pull request that settled it. Where the whole decision is in `docs/design/android-setup/decisions.md`, the entry here gives the part that holds for the desktop too and points there.

- **2026-11-02, #313 (PR #318): a file of a newer version is its own problem kind.** A settings file written by a newer version of the app is `ConfigProblem.Kind.NEWER_VERSION`, with `Stored.Reason.NEWER_VERSION` for the other files, not a text in the problem's detail. The desktop shows it as it shows any unusable config; the Android app opens its "update the app" screen.
- **2026-11-02, #313 (PR #318): a file of a newer version is never written over, removed or set aside.** The engine refuses it itself, in `StoredFile`, for both apps; a write, a removal or a set-aside then fails with an `IOException` and the file stays byte for byte as it was. This holds for every file the engine keeps with a version (`engine.json`, `battery.json`, `trips.json`, `away.json`, `secrets.json`, `trip-notices.json`) and for the desktop's `app.json`, not only for the settings file. Accepted consequences: with such a file, a desktop dashboard change (battery, trips, away) fails with only a log line, as any disk failure there does; `announced.json` has no version (the decision on #313 named it among the versioned files, PR #318 found it has none), so an older app may write over it and an announcement may come twice after a restart, which the maintainer accepts, while `trip-notices.json` has one, so a trip start notice is not repeated that way (the forecast caches `forecast-<id>.json` have no version either); a desktop Settings save can store the keys and `engine.json` before `app.json` is refused, and then shows a failure. The alternative, only `engine.json` refused and the others moved aside and replaced as before, was not chosen. A file this version cannot use for any other reason is still moved aside to `<name>.damaged-<time>` before a new one is written.
- **2026-11-02, #313 (PR #318): "Set up again" moves the damaged settings file aside.** `Engine.setConfigAside()` renames `engine.json` to `engine.json.damaged-<time>` in the same folder (the time in UTC as `yyyyMMdd-HHmmss`, with `-2`, `-3` and so on when that name is taken) and returns the new path, so the message can name it; the engine is then not set up. Only a plain file is moved, and never one of a newer version. Today only the Android app offers "Set up again", after the owner confirms; the desktop has no such button.
- **2026-11-02, #313: typed values are checked against the engine's rules only.** A value the owner types is refused when the engine's own rules refuse it (`InvalidSetting`, `Percent`, the whole-minute rules), as an error under its field; nothing is clamped or rounded. The desktop's own, narrower ranges are not used on Android. Making the engine the one source of these ranges for both apps is #317, still open.
- **2026-11-02, #313: a decimal in a whole-number field is an error.** The amps and the fields in minutes refuse a number with decimals, even `,0`, with their own problem, "Type a whole number, without decimals."; nothing is rounded, and those fields get a keypad without a decimal mark. This is the Android app's form logic (`NumberText.readWhole`).
- **2026-11-02, #313 (PR #318): a failed save stays until a screen has shown it.** The Android app keeps each save's outcome in the app's scope until a screen has shown it, oldest first (`Saves.lastOutcome`, `Saves.shown`), so a later success never takes a failure's place: the owner sees the failure first, then the success. Only an unshown outcome that equals a later one is replaced by it. The alternative, the latest outcome wins, was not chosen.
- **2026-11-05, #359: the round and `ForecastUse`.** `Engine.round(ForecastUse)` is one planning round in public. The desktop's schedule calls it every minute with `ASK_PROVIDERS`, as before; with `STORED_ONLY`, which only the Android app's background work uses, it never asks a provider and reads no API key, and plans from the stored forecast while that is still useful. The whole decision: [android-setup/decisions.md](../android-setup/decisions.md), the entries of #359.
- **2026-11-05, #359: `refreshFailed`.** Each provider's forecast cache file also keeps whether the provider failed when it was last asked, written with the file, cleared by its next answer and not by a settings save. Only a stored-only round reads it, and then tells that forecast as stale, so nothing is announced. A round that asks, the desktop's, reads no such mark, so the desktop is unchanged. A check from the set-up or Settings form (`Engine.preview`) never writes it. The whole decision: [android-setup/decisions.md](../android-setup/decisions.md), the entries of #359.
- **2026-11-05, #359: a refused key.** A 401 or 403 from a provider is `ProviderError.KeyRefused`; `Outlook.NoForecast.keyRefusedBy` and `ForecastSource.keyRefusedBy` on a plan name the providers that refused their key, also while a fallback answered or an older forecast is still used, until the provider answers again or the keys or settings are saved. A stored-only round never says so, as it asks nobody. The engine gives it to both apps; only the Android app reads `keyRefusedBy`, and shows it as a separate warning on the dashboard, also while a fallback or an older forecast still gives a plan, and as a problem for its Problems notification (#361). The desktop shows the provider's own refusal message as the detail under "No forecast" (`OutlookMapper`, `ProviderAttempt`) and in the connection check (the engine's `ConnectionCheck`, which the Android set-up and Settings use too), not while a plan is still given. The whole decision: [android-setup/decisions.md](../android-setup/decisions.md), the entries of #359 and #361.
- **2026-11-05, #359: `nextNoticeDue`.** `Engine.nextNoticeDue(Outlook)` gives the earliest moment at which a window not announced yet (its start minus the lead time) or a trip's grid charge start is due, by the same rules a round tells them; a moment at which the forecast would be stale or more than 6 hours old is left out, and the battery check and a short trip are not part of it, as they wait for the rounds that come anyway. Only the Android app calls it, to set its alarm (#362); the desktop makes a round every minute and does not need it. The whole decision: [android-setup/decisions.md](../android-setup/decisions.md), the entries of #359 and #362.
- **2026-11-09, #389: one factory for the engine and the built-in providers.** Both apps make their engine with `Engine.inFolder`, which puts the engine's files in one data folder (the forecast cache in `forecasts`, `announced.json`, `trip-notices.json`, `away.json`, `trips.json`, `battery.json`; these names are the factory's alone) and gives it `Providers.standard`. It comes in two: `inFolder(dataFolder, ...)` keeps the settings file, `Engine.CONFIG_FILE_NAME` (`engine.json`), in the data folder too, which the Android app uses; `inFolder(dataFolder, configFile, ...)` takes the settings file's path, which the desktop uses, as its settings file is in its config folder or the file named with `--config=`, not in the data folder. Each platform passes the rest: the http client, `PrivateFiles`, its own `ApiKeys`, the notifier, the clock (the desktop `Clock.systemUTC()`, Android the app's clock) and its own single-thread daemon "planner" executor, as the engine makes no thread (ADR 0005). The factory does no I/O and adds no checks: nothing is created, read or checked until the engine's first read or write, and no argument may be null. `Providers.standard(http)` gives Open-Meteo, then Forecast.Solar; the order is the order both apps offer the providers in, and the first is the primary provider set-up drafts on both apps (the desktop's `SetUpWindow` and Android's `SetUpSession` take the first offered). A new provider is added there once (docs/providers.md). The factory keeps ADR 0005's one composition root per app: it is a static method without state of its own that each app's root calls, and each root still makes and passes the parts that differ per platform. `Providers.standard` is the one class in `engine.forecast` that knows the providers' classes; `EngineArchitectureTest` holds it to that, and the desktop's `ArchitectureTest` keeps the providers out of every class outside `engine.forecast`.
- **2026-11-09, #400 (part 1 of #341): the dashboard's model starts in the engine, with the solar chart and `DayName`.** `Outlook.Planned.dashboard(away, trips)` hands the plan's own parts (when it was made, the home's zone, the days, the baseload) to `engine.dashboard` in one input record, `PlanParts`, to which the later parts add theirs, and gives a `DashboardView`: one `DashboardDay` per plan day, each with its `DayName` and its `DayChart`. `DashboardDay` names its day once, through `DayName`, which holds the date. The package-private `ChartBuilder` makes the charts. The later parts of #341 add the day card, the battery, the grid and trip advice, the footer, the away periods and the trips to these records. Nothing in it reads the clock: "now" is the moment the plan was made (`theEngineReadsNoClock`). `Planned` hands its parts over because `engineSubPackagesDoNotReachUpIntoTheEngine` keeps `engine.dashboard` from the root package. The chart's rules, which both apps had each in their own copy and which agreed, are the engine's alone, with private constants: the hours shown from the hour before the first sun to the hour after the last within the day (more than 0.01 kW is sun), 06:00 to 20:00 (real hours from the day's start) for a day without sun or without a forecast; the steps that overlap those hours; the windows; the baseload; one kW scale for every day, the whole kW above the highest sun or the baseload and at least 1; "now" on today only, within the hours shown, their edges included; every whole clock hour as a tick, by real hours from the day's start (23 or 25 on a clock change day, without the hour the clocks skip); the peak, the first of equal ones. Each app picks which ticks it marks (the desktop every third hour, Android as many as fit) and writes the words. `DayName` (today, tomorrow or another day, each with its date) is named from the day the plan was made in the home's zone; the desktop's `Messages` and Android's words, notices and entries take it. `plan.Hours` became public, so the dashboard reckons hours as the planner does.
- **2026-11-09, #401 (part 2 of #341): the day card and the battery in the engine.** Each `DashboardDay` now has, besides its name and chart, its main window as `MainCharge` (the plan's first `Window` of the day, with its grid energy only from 0.05 kWh up, as less is within the forecast's precision), its later windows, why it has no window (`NoWindowReason`), its `BatteryLevels` and, on today only and only while the level is assumed, the assumed level. Its `DayKind` is not stored but derived by `DashboardDay.kind()` (`SOLAR` with a main window, `GRID` for the grid advice's day without one, `NONE` otherwise), so the kind has one source and cannot disagree with the window or the reason. `DashboardView` has the plan's `madeAt` and `zone`, so a client writes its words from the view alone, and the `ChargeLevels` (minimum, target) once. The package-private `DayBuilder` makes the days, with the rules both apps had, which agreed line by line: why a day has no window is, in this order, the grid advice's day (`GRID`) whatever the trips; the day a trip the plan advises on leaves (`DEPARTURE`), on which the card says nothing, as the trip's advice tells what the battery needs; a day the car is away on a stored trip made with it (`AWAY`, by `Trip.covers`, a trip under way and one back at midnight as the trip rules have them); otherwise `NOT_NEEDED`. Departure days come from the plan's trip advice only; the stored trips, which `Planned.dashboard(away, trips)` hands over in `PlanParts` with the battery level, whether it is assumed, the grid and trip advice and the charge levels, only keep the car away. The `BatteryLevels` components carry the unit in their names (`startPct`, `afterPct`, `afterTripPct`, and `minimumPct`, `targetPct` of `ChargeLevels`), and `MainCharge.gridKwh` is an `OptionalDouble`, not an `Optional<Double>`. On a departure day `afterTripPct` is the plan's end level. `BatteryLevels.chargesBeforeTrip()` is derived from the start and the level after charging, one source with no flag to keep in step: it is true when the start and the level after charging differ in whole percent, rounded half up, as both apps write them (a level is 0 to 100, so a tie is an exact half); it replaces the comparison of the written texts both apps made (the Android side of this is in [android-setup/decisions.md](../android-setup/decisions.md), the #401 entry). Each app keeps only the words and the drawing: the desktop's `DayMapper` and `BatteryMapper` take the view, and its own `DayKind` gave way to the engine's; Android's `DayMapper` and day model went, its screens take `DashboardDay`, and after a trip or away change it makes the engine's dashboard again at once from the plan it shows (decision 10 of #341). Whether a level can be entered follows from the day's `DayName` (today).
- **2026-11-09, #402 (part 3 of #341): the grid advice in the engine.** `DashboardView.gridAdvice` is the plan's grid advice as the dashboard shows it, a `GridAdviceView`, empty when the plan gives none: the day it is about as a `DayName`, the energy, the end level (a `double`, below 0 when the driving needs more than the battery holds), and, when a day has room, the window as `GridWindow` (a record of its own) with its day as a `DayName` (by its start in the home's zone) and the charge limit, which comes with the window so neither can be there without the other. `runsEmpty()` is derived: the end level is 0 or less. The advice has no minimum of its own: the words read the plan's (`DashboardView.levels().minimumPct()`), which is not made again from the end level and the deficit as both apps did; this is the one change in what shows, a rounding hair at most, as the desktop did not clamp the sum and Android clamped it to 0–100 (decisions 12 and 15 of #341). `GridAdvice` itself is unchanged. The package-private `GridAdviceBuilder` makes it; the rules, which agreed in both apps but for that sum, are the engine's alone. The record checks that the energy is finite and more than 0, that the end level is finite, and that the window is not on a later day than the one it is for, as `GridAdvisor` gives them; that the end level is below the plan's minimum is checked by `DashboardView`, which has both. Each app keeps only the words: the desktop's `GridAdviceMapper` takes the home's zone and the plan's levels and maps the view, also for the tray's tooltip, which makes the dashboard from the plan without the stored away periods and trips, as the grid advice does not depend on them (a test pins that, with away periods and a trip on the advice's day); Android's `GridAdviceModel` went, `Dashboard.gridAdvice` reads the view and `DashboardWords` writes the words. That the grid advice shows on today's tab stays with each app's screen.
