# Engine: decisions

Decisions about the engine that both apps share, the desktop app and the Android app, that the code alone does not explain. Each says what holds now and ends with the issue that settled it. Where the whole decision is in `docs/design/android/`, the rule here gives the part that holds for the desktop too and points there.

### Files of a newer version, and damaged files

- A settings file written by a newer version of the app is the problem kind `ConfigProblem.Kind.NEWER_VERSION`, any other such file `Stored.Reason.NEWER_VERSION`, not a text in the problem's detail. The desktop shows it as any unusable config; the Android app opens its "update the app" screen (#313).
- A file of a newer version is never written over, removed or set aside. The engine refuses it itself, in `StoredFile`, for both apps: the write, removal or set-aside fails with an `IOException` and the file stays byte for byte as it was. This holds for every file the engine keeps with a version (`engine.json`, `battery.json`, `trips.json`, `away.json`, `secrets.json`, `trip-notices.json`) and for the desktop's `app.json` (#313).
- Accepted consequences: with such a file a desktop dashboard change (battery, trips, away) fails with only a log line, as any disk failure there does; a desktop Settings save can store the keys and `engine.json` before `app.json` is refused, and then shows a failure (#313).
- `announced.json` and the forecast caches `forecast-<id>.json` have no version, so an older app may write over `announced.json` and an announcement may come twice after a restart, which is accepted; `trip-notices.json` has one, so a trip start notice is not repeated that way (#313).
- A file this version cannot use for any other reason is moved aside to `<name>.damaged-<time>` before a new one is written (#313).

### Panel arrays: count, power per panel and year

- The settings file is version 2. A panel array has either `kwp` or `count` with `wpPerPanel`, `yearPlaced` or both; one with both kinds is refused, and an empty power per panel is not stored. A version 1 file is read as it is, and 0.6.0 refuses a version 2 file as written by a newer version (#448).
- #449 (the place name) lands under the same settings file version 2 as #448, so the two are released together (#448, #449).
- The place name is `HomeSystem.place()`, an optional `PlaceName` beside the coordinates, written as the system's `placeName` only when there is one: trimmed, at most 100 characters (code points), blank read as none, longer refused. A file without it reads as before; a hand-edited name that does not fit its coordinates is trusted. Every change of the location says what becomes of the name: `withPlace` with one, `withUnnamedLocation` without, so no name stays with other coordinates (#449).
- A client decides the name by comparing the coordinate fields with the chosen place's at the fields' four decimals; a label longer than 100 characters is cut there (`PlaceName.fromLabel`), as a search result's label has no limit (#449).
- A place name holds no control character (line breaks and tabs among them), no line or paragraph separator (U+2028, U+2029) and no direction control (U+200E, U+200F, U+061C, U+202A to U+202E, U+2066 to U+2069): such a character would break the one line the name is shown on, or turn the text around it the other way. The constructor refuses one, also in a file; `PlaceName.fromLabel` makes each a space, as a search result's label is not ours to refuse. The zero-width non-joiner and joiner stay allowed, as Persian and Indic names need them (#449).
- `PanelArray.size()` is a `PanelSize`, `Peak` or `Panels`; `PanelArray.kwp()` follows from it, so the planner and the providers still get a kWp. The typical power per year placed is `PanelSize.Panels.typicalWattPeak`, one table for both apps, and `typicalWattPeakFor` gives the estimate a form shows, empty for a year before 1990 or after this year (#448).
- The count is 1 to 200, the power 50 to 1000 Wp, both whole, and the year 1990 or later, each with its own `ConfigSetting` and `InvalidSetting.Rule`. A file is read without a clock, so a later year is refused only where an app enters it: `Panels.notPlacedAfter(Engine.thisYear(deviceZone))`, the year on the device's clock: the engine's clock in the device's time zone, which the app hands in, so the owner can enter the new year from midnight on 1 January, local time. Only an array whose count, power or year the owner changed is checked; one left alone is saved as it was read, also when its year is after this one (#448).
- The choices are the engine's `TiltChoice` (13, 35, 50 and 90 degrees) and `CompassPoint` (eight, clockwise from north, which is stored as 180). A stored value shows as the nearest choice, the steeper tilt or the direction furthest from south on a tie, and stays stored until the owner chooses (#448).

### Setting the settings file aside

- `Engine.setConfigAside()` renames `engine.json` to `engine.json.damaged-<time>` in the same folder (the time in UTC as `yyyyMMdd-HHmmss`, with `-2`, `-3` and so on when that name is taken) and returns the new path, so the message can name it; the engine is then not set up. Only a plain file is moved, never one of a newer version (#313).
- Only the Android app offers "Set up again", after the owner confirms; the desktop has no such button (#313).

### The Android app's forms

- A typed value is refused only when the engine's own rules refuse it (`InvalidSetting`, `Percent`, the whole-minute rules), as an error under its field; nothing is clamped or rounded. The desktop's own, narrower ranges are not used on Android; one source of these ranges for both apps is the open #317 (#313).
- The amps and the fields in minutes refuse a number with decimals, even `,0`, with "Type a whole number, without decimals."; nothing is rounded, and those fields get a keypad without a decimal mark (`NumberText.readWhole`) (#313).
- Each save's outcome is kept in the app's scope until a screen has shown it, oldest first (`Saves.lastOutcome`, `Saves.shown`), so a later success never takes a failure's place. Only an unshown outcome that equals a later one is replaced by it (#313).

### The house's use

- The settings file keeps the baseload as `baseloadKw`, the average over the whole day; `House.TYPICAL` stays 0.5 kW. The planner and the dashboard's chart use the kW, and the chart's legend stays "House" (#450).
- Both apps show it as "Household use" in kWh per day: the stored kW times 24, with one decimal (12.0 for the typical value). A field the owner did not change, or changed back to the text it showed, gives the stored kW back exactly, so a save never drifts; a typed value is divided by 24 (#450).
- The desktop's field keeps 0 to 480 kWh per day (20 kW), bringing a value outside it into the range as its other number fields do. Android refuses only what the engine refuses, a negative use, with the out-of-range text, and keeps a stored use over 20 kW as it was read; the bound both apps share is the open #317's (#450).
- Neither app's set-up asks for it: set-up saves the typical value as a typical value. In Settings the field and its "I don't know" sit under the "More settings" fold of the Car and house page, closed when the page loads; on Android a problem in the field opens the fold and holds it open until the next check finds none; the desktop's field keeps every value in its range, so it has no problem to show and its fold never opens by itself. On the desktop the unit "kWh per day" is a text of its own (`UNIT_KWH_PER_DAY`) (#450).
- The car's trip surcharge shares that fold, before the household use, in both apps' Settings, and on Android also on set-up's Car step; the car's "I don't know" stays outside it, after the daily distance. The desktop's trip surcharge keeps 0 to 100 %, so its fold still never opens by itself; the desktop's set-up does not show the trip surcharge (#452).

### Typical values

- Since 2026-11-12 no field in either app shows that it holds a typical value: the "Typical value" tag is gone from set-up and Settings, and with it the screen reader's sentence on Android. Which values are typical is still kept, in the forms (the desktop's `TypicalMarks`, Android's `FormState`), in Android's saved state and in the settings file's `typical` section, whose format does not change; set-up's "Choose…" for the charge power and its empty panel array still follow it (#458).

### The charge power at home

- The settings file keeps the charger as before: phases, lowest and highest current, voltage and efficiency. Both apps show it first as the charge power at home, the engine's `HomeChargePower`, with "Other" next to them in `ChargePowerChoice`, what the drop-down holds: 3.7 kW (one phase, 16 A), 7.4 kW (one phase, 32 A), 11 kW (three phases, 16 A) and 22 kW (three phases, 32 A), all at 230 V, or "Other". Each label is one text per power and language, never a number put into a pattern (#451).
- A charger is a power when its phases and highest current are the power's and its voltage is 230 V exactly (`ChargePowerChoice.matching`, `of`); the lowest current and the efficiency play no part. Anything else, such as 240 V, three phases of 25 A or one phase of 25 A, is "Other": nothing is rounded to the nearest power, so the page never shows a kW that is not true (#451).
- Choosing a power sets the phases, the highest current and 230 V; the lowest current and the efficiency keep their values, also exactly when left alone. A highest current that then ends below a typed lowest one shows the existing problem at the highest current; nothing else is changed. The drop-down shows the power the values stand for, else "Other"; choosing "Other" changes no value and opens the fold, and shows "Other" until the phases, the highest current or the voltage change (#451).
- The phases, the currents, the voltage, the efficiency and "I don't know" are under "More settings", closed on a power and open on "Other" as the page loads, and open while a field under it shows a problem. On the desktop the number fields keep every value in their ranges, so the one problem under the fold is a highest current below the lowest; on Android every engine refusal and unreadable number of those fields is one. "I don't know" fills in the lowest current, the voltage and the efficiency only (#451).
- In set-up the power starts with "Choose…" while the stored phases and highest current are typical values, and set-up does not go on until one is chosen ("Choose one." at the field, gone as soon as a power or "Other" is chosen), as the phases decide from how much solar power the car can charge; the folded fields start at their typical values. Only a choice in the drop-down ends "Choose…". A choice takes the typical mark from the phases and the highest current, and from the voltage only when it changed (#451).
- On the desktop, when set-up is built again from its draft (another language on the App step, or an app setting saved in Settings while set-up is open), a chosen "Other" comes back as "Choose…" while the phases and the highest current are untouched: the draft is the config, which remembers the choice only through the typical marks it took away, and "Other" takes none. A chosen power survives. Android keeps the choice itself in its saved state, so there it comes back (#451).

### The notification lead time

- The settings file keeps the lead as before, `notifyLeadMinutes`, any whole number from 0. Both apps offer it as a drop-down of the engine's `NotifyLeadChoices.STANDARD`: at the start, or 5, 10, 15, 30 or 60 minutes ahead (#452).
- A stored lead that is none of them, such as 20 minutes, is offered too, in its place by length, while it is the one chosen (`NotifyLeadChoices.offered`), so it shows as "20 minutes ahead" and is saved as it is; once another is chosen, it is no longer offered. Nothing is rounded to the nearest choice (#452).
- On the desktop the Planning page's other number fields keep every value in their ranges, so the fold with the planning margin, the import tolerance and the minimum charge window never has a problem and never opens by itself; on Android an unreadable number or an engine refusal there opens it (#452).

### Rounds and the stored forecast

- `Engine.round(ForecastUse)` is one planning round in public. The desktop's schedule calls it every minute with `ASK_PROVIDERS`. `STORED_ONLY`, used only by the Android app's background work, never asks a provider, reads no API key, and plans from the stored forecast while that is still useful. The whole decision: [android/notifications.md](../android/notifications.md) (#359).
- Each provider's forecast cache file also keeps whether the provider failed when last asked (`refreshFailed`): written with the file, cleared by its next answer, not by a settings save. Only a stored-only round reads it, and then tells that forecast as stale, so nothing is announced; the desktop's rounds, which ask, read no such mark. `Engine.preview` (the set-up and Settings check) never writes it (#359).
- `Engine.nextNoticeDue(Outlook)` gives the earliest moment at which a window not announced yet (its start minus the lead time) or a trip's grid charge start is due, by the rules a round tells them. A moment at which the forecast would be stale or more than 6 hours old is left out; the battery check and a short trip are not part of it, as they wait for the rounds that come anyway. Only the Android app calls it, to set its alarm (#359).
- A notification lead time of 0 tells a window when a round first sees it begun: a running solar window begins at each round's moment, so it is told as soon as it is seen, also after a while. Where the start is fixed, a trip's planned grid charge, it is told from the start for 10 minutes at most (`AT_START_GRACE`: a round or Android's alarm may be late), never past the window's end. `nextNoticeDue` gives the start while it is to come and now inside that time; leads above 0 get no grace (#360).

### A refused API key

- A 401 or 403 from a provider is `ProviderError.KeyRefused`. `Outlook.NoForecast.keyRefusedBy` and `ForecastSource.keyRefusedBy` name the providers that refused their key, also while a fallback answered or an older forecast is still used, until the provider answers again or the keys or settings are saved. A stored-only round never says so, as it asks nobody (#359).
- Both apps read `keyRefusedBy` for a separate warning on the dashboard, also while a fallback or an older forecast still gives a plan (#359, #391). Neither the desktop's tray icon nor its notifications say it (#391).
- The Android app's Problems notification counts a refused key as a problem (#361).
- The desktop shows the provider's own refusal message as the detail under "No forecast" (`OutlookMapper`, `ProviderAttempt`) and in the connection check (the engine's `ConnectionCheck`, which the Android set-up and Settings use too), not while a plan is still given (#359).
- The desktop's dashboard warns above the day card on every day's tab, or above "No forecast" (also for a forecast without days), in Android's words: one card with a line per provider, in the order they were asked, named as `ProviderInfo` names it (by its id when the app does not know it). Before the first plan and without a usable set-up there is none. Set-up's preview of the dashboard leaves it out, as its words point to Settings while the owner is still in set-up (#391).

### The engine factory

- Both apps make their engine with `Engine.inFolder`, which gives it `Providers.standard` and puts its files in one data folder: the forecast cache in `forecasts`, `announced.json`, `trip-notices.json`, `away.json`, `trips.json`, `battery.json`; these names are the factory's alone (#389).
- `inFolder(dataFolder, ...)` keeps the settings file, `Engine.CONFIG_FILE_NAME` (`engine.json`), in the data folder too (Android). `inFolder(dataFolder, configFile, ...)` takes its path (desktop), as the desktop's settings file is in its config folder or named with `--config=` (#389).
- Each platform passes the rest: the http client, `PrivateFiles`, its own `ApiKeys`, the notifier, the clock (the desktop `Clock.systemUTC()`, Android the app's clock) and its own single-thread daemon "planner" executor, as the engine makes no thread (ADR 0005) (#389).
- The factory does no I/O and adds no checks: nothing is created, read or checked until the engine's first read or write. No argument may be null (#389).
- The factory keeps ADR 0005's one composition root per app: a static method without state that each app's root calls, while each root makes and passes the parts that differ per platform (#389).
- `Providers.standard(http)` gives Open-Meteo, then Forecast.Solar: the order both apps offer them in, and the first is the primary provider set-up drafts on both apps (`SetUpWindow`, `SetUpSession`). A new provider is added there once ([docs/providers.md](../../providers.md)) (#389).
- `Providers.standard` is the one class in `engine.forecast` that knows the providers' classes (`EngineArchitectureTest`); the desktop's `ArchitectureTest` keeps the providers out of every class outside `engine.forecast` (#389), and `EngineArchitectureTest` out of the engine's own parts outside it, when the engine is built alone (#285).
- Each of the engine's file classes (`ConfigFile`, `AwayFile`, `TripFile`, `BatteryFile`, `SecretsFile`, `AnnouncedWindows`, `ToldTrips`, `ForecastCache`) and the desktop's `AppSettingsFile` takes a `Clock`, which `StoredFile` names a file set aside with; `StoredFile` has no constructor that reads the system's clock any more. `Engine.inFolder` hands its clock on to the files it makes; each app's composition root passes its own where it makes one itself (#285).
- `EngineArchitectureTest` holds the engine's classes, when built alone, to its own copies of the desktop `ArchitectureTest`'s rules for every class: on `java.util.logging`, the console, stack traces, the system locale, the locale of texts, numbers and times, system properties and the environment, the user interface, and the providers. Copies, not a shared factory: the rules differ per module by their exceptions, which the engine's have none of, and each copy has its own class that breaks it. The desktop's rules stay as they are, so the full build checks the engine's classes twice (#285).

### Fetching from the web

- Every request of either app carries `HttpGet.USER_AGENT` as its User-Agent: the app's name and its home page, one text in the engine, so the services see one app, without a device or a version (#309).
- A body that ends before its `Content-Length` is an `IOException` in both apps, as soon as the server hangs up, never a shorter body as if it were whole; `HttpGetContractTest` checks it with a plain socket, as `com.sun.net.httpserver` cannot send such an answer (#309).
- A 1xx, 204 or 304 answer with a `Content-Length` is not part of the contract (decided 2026-11-13): Java's client refuses such a 204 before `JdkHttpGet` sees it, a final 1xx reaches neither client, and no provider sends a conditional request. `AndroidHttpGet` keeps its own rule, an empty body for them, with its own test (#309).

### The dashboard model

The decisions of the assumption checks behind this model are comments on #341 and #404.

- The dashboard's rules are the engine's alone, in `engine.dashboard`; each app keeps only the words and the drawing (#400).
- `Outlook.Planned.dashboard(away, trips)` hands the plan's parts to `engine.dashboard` in one input record, `PlanParts`, because `engineSubPackagesDoNotReachUpIntoTheEngine` keeps `engine.dashboard` from the root package, and gives a `DashboardView` with one `DashboardDay` per plan day (#400).
- Nothing in `engine.dashboard` reads the clock: "now" is the moment the plan was made (`theEngineReadsNoClock`). Hours are reckoned with the public `plan.Hours`, as the planner does (#400).
- `DashboardView` has the plan's `madeAt` and `zone`, so a client writes its words from the view alone, and the `ChargeLevels` (minimum, target) once (#401).
- `DashboardDay` names its day once, through `DayName` (today, tomorrow or another day, each with its date), named from the day the plan was made in the home's zone. The desktop's `Messages` and Android's words, notices and entries take it (#400).
- Today in the home's zone is derived once, by `PlanParts.today()`, which the builders use; `DashboardView`, which holds no `PlanParts` but the moment and the zone, keeps its own private derivation rather than a `today` component in a public record (#405).

### The solar chart

- The package-private `ChartBuilder` makes each day's `DayChart`, with private constants: the hours shown from the hour before the first sun to the hour after the last within the day (more than 0.01 kW is sun), 06:00 to 20:00 (real hours from the day's start) for a day without sun or without a forecast; the steps that overlap those hours; the windows; the baseload; one kW scale for every day, the whole kW above the highest sun or the baseload and at least 1; "now" on today only, within the hours shown, their edges included; every whole clock hour as a tick, by real hours from the day's start (23 or 25 on a clock change day, without the hour the clocks skip); the peak, the first of equal ones (#400).
- Each app picks which ticks it marks (the desktop every third hour, Android as many as fit) and writes the words (#400).
- The desktop's `SolarChartModel` holds the engine's `DayChart` with only its words (the scale, a readout per step, the labelled ticks, the spoken sentence) and none of its records or checks; `SolarChart` and `CurvePoints` draw from the `DayChart`, and which step an hour falls in (`stepAt`) and a step's middle stay the desktop's, as Android has its own. The apps' code calls the chart's dashed line the baseload, while its legend and sentence keep "House" ("Huis") (#405).

### The day card and the battery

- Each `DashboardDay` has its name, its chart, its main window as `MainCharge` (the plan's first `Window` of the day, its grid energy only from 0.05 kWh up, as less is within the forecast's precision), its later windows, why it has no window (`NoWindowReason`), its `BatteryLevels` and, on today only while the level is assumed, the assumed level (#401).
- `DayKind` is derived by `DashboardDay.kind()`, not stored (`SOLAR` with a main window, `GRID` for the grid advice's day without one, `NONE` otherwise), so it cannot disagree with the window or the reason (#401).
- The package-private `DayBuilder` makes the days. Why a day has no window is, in this order: the grid advice's day (`GRID`) whatever the trips; the day a trip the plan advises on leaves (`DEPARTURE`), on which the card says nothing, as the trip's advice tells what the battery needs; a day the car is away on a stored trip made with it (`AWAY`, by `Trip.covers`, a trip under way and one back at midnight as the trip rules have them); a day a grid charge starts on (`GRID_CHARGE_STARTS`); then `NOT_NEEDED` or `TOO_LITTLE_SOLAR` (#401, #460).
- Each `DayPlan` hands over `chargeToPct`, the level the day's solar charging aims at: the highest cap of the day's parts, which is the target, or more on a day the plan charges above it for a trip (from the trip's first day of charging above the target), and on a day with a departure the highest of its parts before and after it. A trip's grid charge does not raise it: the day it starts on never reaches the comparison below (#460).
- `GRID_CHARGE_STARTS` is a day a grid charge starts on, by the start of its window in the home's time zone: a trip's (its advice's grid window, a planned one or one that starts now), or the grid advice's when its window found room only on a day before the one it is about (`GridAdvisor` places it on the latest day up to the dip with room). The card says only "No charge window" and shows the battery chip, as on a departure day, and gives no sentence: no reason is always true. A battery already full has no use for the sun, and the day's own driving may be what makes the grid charge needed, so "too little solar power" can be untrue, and "Charging not needed" would contradict the advice beside it. The rule reads the advice the plan already hands over, so `DayPlan` carries nothing more for it (#460).
- Any other such day is `NOT_NEEDED` when the level it starts from, rounded half up as both apps show it, is at or above `DayPlan.wholeChargeToPct()`: `chargeToPct` rounded up to a whole percentage, as the trip advice gives its level to charge to (`TripAdvice.chargeLimitPct`), with the plan's millionth of a point of rounding; otherwise `TOO_LITTLE_SOLAR`. So 79.6 % with a target of 80 % needs no charging, and 92 % below a trip's 92.1 % has too little solar power, as the advice says to charge to 93 %. The level after charging is not compared, as a trip's grid charge raises it on a day without a window (#460).
- Whether the day card shows the day's battery levels is derived by `DashboardDay.showsBattery()`: with a main window and for `GRID`, `DEPARTURE`, `AWAY` and `GRID_CHARGE_STARTS`, not for `NOT_NEEDED` and `TOO_LITTLE_SOLAR`, whose heading says all and beside which the Car battery card has the levels. Android's `SourceFigure` calls it for every day and the desktop's `DayMapper` for a day without a window, as a day with one always shows them; neither keeps a list of reasons of its own (#460).
- `TOO_LITTLE_SOLAR` covers every cause the planner cannot tell apart: the sun is gone for today, the car is away in the sun hours, no stretch is long or strong enough for the charger, or the forecast is weak. `DayKind` stays `NONE` for it, `NOT_NEEDED` and `GRID_CHARGE_STARTS`; notifications, the trip advice and the tray do not read the reason (#460).
- Departure days come from the plan's trip advice only; the stored trips only keep the car away (#401).
- The `BatteryLevels` components carry the unit in their names (`startPct`, `afterPct`, `afterTripPct`, and `minimumPct`, `targetPct` of `ChargeLevels`); `MainCharge.gridKwh` is an `OptionalDouble`, not an `Optional<Double>`. On a departure day `afterTripPct` is the plan's end level (#401).
- `BatteryLevels.chargesBeforeTrip()` is derived, with no flag to keep in step: true when the start and the level after charging differ in whole percent, rounded half up, as both apps write them (a level is 0 to 100, so a tie is an exact half). Neither app compares its written texts instead ([android/dashboard.md](../android/dashboard.md)) (#401).
- Whether a level can be entered follows from the day's `DayName` (today) (#401).
- The desktop's `DayMapper` and `BatteryMapper` take the view and use the engine's `DayKind`. Android's screens take `DashboardDay`, and after a trip or away change the app makes the engine's dashboard again at once from the plan it shows (#401).

### The grid advice

- `DashboardView.gridAdvice` is a `GridAdviceView`, empty when the plan gives no grid advice: the day it is about as a `DayName`, the energy, the end level (a `double`, below 0 when the driving needs more than the battery holds), and, when a day has room, the window as `GridWindow` with its day as a `DayName` (by its start in the home's zone) and the charge limit, which comes with the window so neither is there without the other. `runsEmpty()` is derived: the end level is 0 or less (#402).
- The advice has no minimum of its own: the words read the plan's (`DashboardView.levels().minimumPct()`), not one made again from the end level and the deficit (#402).
- The package-private `GridAdviceBuilder` makes it. The record checks that the energy is finite and more than 0, that the end level is finite, and that the window is not on a later day than the one it is for, as `GridAdvisor` gives them; `DashboardView`, which has both, checks that the end level is below the plan's minimum (#402).
- The desktop's `GridAdviceMapper` takes the home's zone and the plan's levels and maps the view, also for the tray's tooltip, which makes the dashboard without the stored away periods and trips, as the grid advice does not depend on them; a test pins that, with away periods and a trip on the advice's day (#402).
- On Android `Dashboard.gridAdvice` reads the view and `DashboardWords` writes the words (#402).

### The trip advice

- `DashboardView.tripAdvice` holds one `TripAdviceView` per trip the plan advises on, in order of departure: the trip, its departure day as a `DayName`, what the plan does as a `TripPlan`, and `shortKm`, an `OptionalDouble` in km, present and more than 0 when the battery falls short. Each app rounds it up in its own unit, the desktop in km or miles, Android in km (#403).
- The battery level the plan starts from and whether it is assumed are on the view once, not on every advice: `DashboardView.startLevel`, a `StartLevel` (`levelPct`, `assumed`), which both apps' trip advice words read, as the grid advice's words read `levels` (#403).
- `TripPlan` is a sealed interface with five cases: `Enough` (no grid charge, not short, and no solar windows or the needed level not above the target), `Solar`, `SolarThenGrid`, `Grid` and `Leaves` (neither, and short). It holds the charge limit `chargeLimitPct` from `TripAdvice.chargeLimitPct()`, the solar windows grouped by the day of their start in the home's zone (`SolarDay`, in time order) and the grid charge as `TripGridStart` (#403).
- `TripGridStart` holds the window, `TripGridCharge.Start`, its start's day as a `DayName`, and `when`, the enum `TripGridStart.When`: `NOW` (the window starts no later than the moment the plan was made; named apart from `Start.NOW`, which says why it starts early), `TONIGHT` (after that moment, on its day, at or after 18:00 in the home's zone: the private constant `EVENING` in `TripAdviceBuilder`) or `LATER`. One enum, not two booleans of which only three combinations make sense; `startsNow()` and `tonight()` are derived from it (#403).
- `asksAction()` (not `Enough`), `source()` (the engine's `EnergySource`: `CAR` for `Enough`, `SOLAR` for `Solar` without a shortfall, `GRID` otherwise) and `shownOn(DayName)` (the departure day, and today when it asks an action) are derived, not stored (#403).
- The records check what the builder cannot break: a distance short is finite and more than 0, `Enough` is never short and `Leaves` always is, a day of solar windows and a solar plan are never empty, and a start is not tonight on another day than today (#403).
- The package-private `TripAdviceBuilder` makes them; its rules, 18:00 among them, are the engine's alone (#403).
- `EnergySource` (solar, grid, car) is the engine's, and both apps colour their chips and figures by it. Android's `SourceFigure.kt`, which uses no rule of the dashboard's, is in `ui/home` (#403); since #405 no list of model files is kept (`AppArchitectureTest`), as `home/Dashboard.kt`, the last file on it, holds no rule either.
- Where the advice shows is the model's: `DashboardView.tripAdviceOn(day)` applies each advice's own rule (`TripAdviceView.shownOn`), and `DashboardView.gridAdviceOn(day)` gives the grid advice only on the day named `DayName.Today`. So the desktop too shows the grid advice and the trip advice that asks an action, in the today wording, only on the day named today; a plan made by the engine starts on today (#403).
- On the desktop each `DayModel` carries its own cards, filled per day by `OutlookMapper` from `gridAdviceOn(day)` and `tripAdviceOn(day)`: an `Optional<GridAdviceModel>` and a list of `TripAdviceModel`, in the words of that day's tab (the today wording on the day named `DayName.Today`, the weekdays on any other); its `DashboardView` shows the cards of the day selected. `TripAdviceModel` keeps only the words (#403).
- `TripCard.show` takes the day's date, title and trip rows, not its `DayModel`, so the `day` and `trip` packages do not depend on each other (#403).
- Android's `DashboardWords.tripAdvice` takes the view and the tab's `DayName` (#403).
- Both apps say "tonight" only on today's tab (#403).

### The footer

- `DashboardView.footer` is a `Footer`: the provider's credit as the provider gives it (`credit`); whether the fallback provider stood in (`Fallback`, sealed: `None`, `For(primaryName)`, which refuses an empty name, and `ForUnknown` for a primary without a name); when the forecast was fetched; `stale` (one flag: the freshness is `STALE`); `busyUntil` (present only while the provider's cool-down is after the moment the plan was made; a cool-down that ends at that moment is over); and `keyRefusedBy`, the providers that refused their API key, in the order they were asked (#404).
- `keyRefusedBy` is in the footer because it is where the forecast came from and it reaches a plan without days too; each app only resolves the names (#404).
- A plan without days has no dashboard, so the footer is also made alone: `Footer.of(ForecastSource, madeAt)` and `Outlook.Planned.footer()`, the same as the dashboard's. The desktop's `OutlookMapper` writes it (#404).

### The coming one-off away periods and the trips list

- `DashboardView.away` lists, as `ComingAway`, the stored one-off away periods that end after the moment the plan was made, strictly, in their stored order. `ComingAway` is sealed: `AllDay(day)`, `PartOfDay(day)` and `Days(startDay, endDay)`, which refuses an end day not after its start day, each with the stored `period`; `start()` and `end()` of `PartOfDay` and `Days` come from the period (#404).
- All-day is the period from one local midnight to the next (23 or 25 hours on a clock change day, and 24 hours from midnight then are not all-day); part of a day starts and ends on the same local day; any other is over days, also one that ends at midnight. The days are `DayName`s from the plan's today in the home's zone (#404).
- `DashboardView.trips` lists every stored trip in their stored order, also one under way, one back already and one without this car, as `ListedTrip(trip, departureDay, returnDay)`: the return's own day, so a trip back at midnight returns the next day. It refuses a return day before the departure day; `sameDay()` is derived from the two days (#404).
- Which trips a day lists is `DashboardView.tripsOn(day)`, by `Trip.covers`, the only copy of that rule (#404).
- `DashboardView.describe(OneOffAwayPeriod)` and `describe(Trip)` give one period or trip as the lists do, also one that ended or is not stored; without a view, `ComingAway.describe(period, zone, today)` and `ListedTrip.of(trip, zone, today)` take the day to name from (#404).
- A valid stored period or trip never makes `Days` or `ListedTrip` refuse: in a zone whose local date once ran backwards (America/St_Johns on 7 November 2010, from 00:01 back to 23:01 the day before), a period whose end day is not after its start day is `PartOfDay`, and a trip's return day is the later of the dates of its departure and its return (#404).
- The package-private `ListBuilder` makes the two lists. Their tests hold the boundaries: an away period ending at the moment the plan was made and a second after, a cool-down ending at that moment, all-day on 29 March and 25 October, an away period ending at midnight, a trip back at midnight and a minute after, a zone that is not UTC's, the footer of a plan without days, describing a period that ended (#404).
- On the desktop `OutlookMapper` fills each `DayModel`'s trip rows from `tripsOn(day)`, `TripsModel` keeps the zone and the units, and `OneOffAwayMapper` and `TripMapper` take the engine's rows; neither `TripsModel`, `OneOffAwayModel` nor `OneOffAwayMapper` keeps the moment the plan was made. The Android side is in [android/dashboard.md](../android/dashboard.md) (#404).
