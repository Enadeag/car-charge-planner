# Engine: decisions

Decisions about the engine that both apps share, the desktop app and the Android app, that the code alone does not explain. Newest last; each names the date and the issue or pull request that settled it. Where the whole decision is in `docs/design/android-setup/decisions.md`, the entry here gives the part that holds for the desktop too and points there.

- **2026-11-02, #313 (PR #318): a file of a newer version is its own problem kind.** A settings file written by a newer version of the app is `ConfigProblem.Kind.NEWER_VERSION`, with `Stored.Reason.NEWER_VERSION` for the other files, not a text in the problem's detail. The desktop shows it as it shows any unusable config; the Android app opens its "update the app" screen.
- **2026-11-02, #313 (PR #318): a file of a newer version is never written over, removed or set aside.** The engine refuses it itself, in `StoredFile`, for both apps; a write, a removal or a set-aside then fails with an `IOException` and the file stays byte for byte as it was. This holds for every file the engine keeps with a version (`engine.json`, `battery.json`, `trips.json`, `away.json`, `secrets.json`, `trip-notices.json`) and for the desktop's `app.json`, not only for the settings file. Accepted consequences: with such a file, a desktop dashboard change (battery, trips, away) fails with only a log line, as any disk failure there does; `announced.json` has no version (the decision on #313 named it among the versioned files, PR #318 found it has none), so an older app may write over it and an announcement may come twice after a restart, which the maintainer accepts, while `trip-notices.json` has one, so a trip start notice is not repeated that way (the forecast caches `forecast-<id>.json` have no version either); a desktop Settings save can store the keys and `engine.json` before `app.json` is refused, and then shows a failure. The alternative, only `engine.json` refused and the others moved aside and replaced as before, was not chosen. A file this version cannot use for any other reason is still moved aside to `<name>.damaged-<time>` before a new one is written.
- **2026-11-02, #313 (PR #318): "Set up again" moves the damaged settings file aside.** `Engine.setConfigAside()` renames `engine.json` to `engine.json.damaged-<time>` in the same folder (the time in UTC as `yyyyMMdd-HHmmss`, with `-2`, `-3` and so on when that name is taken) and returns the new path, so the message can name it; the engine is then not set up. Only a plain file is moved, and never one of a newer version. Today only the Android app offers "Set up again", after the owner confirms; the desktop has no such button.
- **2026-11-02, #313: typed values are checked against the engine's rules only.** A value the owner types is refused when the engine's own rules refuse it (`InvalidSetting`, `Percent`, the whole-minute rules), as an error under its field; nothing is clamped or rounded. The desktop's own, narrower ranges are not used on Android. Making the engine the one source of these ranges for both apps is #317, still open.
- **2026-11-02, #313: a decimal in a whole-number field is an error.** The amps and the fields in minutes refuse a number with decimals, even `,0`, with their own problem, "Type a whole number, without decimals."; nothing is rounded, and those fields get a keypad without a decimal mark. This is the Android app's form logic (`NumberText.readWhole`).
- **2026-11-02, #313 (PR #318): a failed save stays until a screen has shown it.** The Android app keeps each save's outcome in the app's scope until a screen has shown it, oldest first (`Saves.lastOutcome`, `Saves.shown`), so a later success never takes a failure's place: the owner sees the failure first, then the success. Only an unshown outcome that equals a later one is replaced by it. The alternative, the latest outcome wins, was not chosen.
- **2026-11-05, #359: the round and `ForecastUse`.** `Engine.round(ForecastUse)` is one planning round in public. The desktop's schedule calls it every minute with `ASK_PROVIDERS`, as before; with `STORED_ONLY`, which only the Android app's background work uses, it never asks a provider and reads no API key, and plans from the stored forecast while that is still useful. The whole decision: [android-setup/decisions.md](../android-setup/decisions.md), the entries of #359.
- **2026-11-05, #359: `refreshFailed`.** Each provider's forecast cache file also keeps whether the provider failed when it was last asked, written with the file, cleared by its next answer and not by a settings save. Only a stored-only round reads it, and then tells that forecast as stale, so nothing is announced. A round that asks, the desktop's, reads no such mark, so the desktop is unchanged. A check from the set-up or Settings form (`Engine.preview`) never writes it. The whole decision: [android-setup/decisions.md](../android-setup/decisions.md), the entries of #359.
- **2026-11-05, #359: a refused key.** A 401 or 403 from a provider is `ProviderError.KeyRefused`; `Outlook.NoForecast.keyRefusedBy` and `ForecastSource.keyRefusedBy` on a plan name the providers that refused their key, also while a fallback answered or an older forecast is still used, until the provider answers again or the keys or settings are saved. A stored-only round never says so, as it asks nobody. The engine gives it to both apps; only the Android app reads `keyRefusedBy`, and shows it as a separate warning on the dashboard, also while a fallback or an older forecast still gives a plan, and as a problem for its Problems notification (#361). The desktop shows the provider's own refusal message as the detail under "No forecast" (`OutlookMapper`, `ProviderAttempt`) and in the connection check (the engine's `ConnectionCheck`, which the Android set-up and Settings use too), not while a plan is still given. The whole decision: [android-setup/decisions.md](../android-setup/decisions.md), the entries of #359 and #361.
- **2026-11-05, #359: `nextNoticeDue`.** `Engine.nextNoticeDue(Outlook)` gives the earliest moment at which a window not announced yet (its start minus the lead time) or a trip's grid charge start is due, by the same rules a round tells them; a moment at which the forecast would be stale or more than 6 hours old is left out, and the battery check and a short trip are not part of it, as they wait for the rounds that come anyway. Only the Android app calls it, to set its alarm (#362); the desktop makes a round every minute and does not need it. The whole decision: [android-setup/decisions.md](../android-setup/decisions.md), the entries of #359 and #362.
- **2026-11-09, #389: one factory for the engine and the built-in providers.** Both apps make their engine with `Engine.inFolder`, which puts the engine's files in one data folder (the forecast cache in `forecasts`, `announced.json`, `trip-notices.json`, `away.json`, `trips.json`, `battery.json`; these names are the factory's alone) and gives it `Providers.standard`. It comes in two: `inFolder(dataFolder, ...)` keeps the settings file, `Engine.CONFIG_FILE_NAME` (`engine.json`), in the data folder too, which the Android app uses; `inFolder(dataFolder, configFile, ...)` takes the settings file's path, which the desktop uses, as its settings file is in its config folder or the file named with `--config=`, not in the data folder. Each platform passes the rest: the http client, `PrivateFiles`, its own `ApiKeys`, the notifier, the clock (the desktop `Clock.systemUTC()`, Android the app's clock) and its own single-thread daemon "planner" executor, as the engine makes no thread (ADR 0005). The factory does no I/O and adds no checks: nothing is created, read or checked until the engine's first read or write, and no argument may be null. `Providers.standard(http)` gives Open-Meteo, then Forecast.Solar; the order is the order both apps offer the providers in, and the first is the primary provider set-up drafts on both apps (the desktop's `SetUpWindow` and Android's `SetUpSession` take the first offered). A new provider is added there once (docs/providers.md).
