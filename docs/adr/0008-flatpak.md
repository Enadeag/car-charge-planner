# The Flatpak: its sandbox, start at login through the portal, and its ID

[ADR 0007](0007-linux-packages.md) chose Flathub as the main way to install on Linux, later (#217). This records how the app runs in the Flatpak sandbox, as its own decision: 0007 is about which packages there are, this one about what the sandbox changes in the app. The files are in `src/packaging/flatpak/`: the manifest, the AppStream metadata, the menu entry and the Maven sources, each named after the app ID as Flathub asks. The manifest goes to the app's repository at Flathub when it is submitted, with its source changed from this working copy to a git tag and its commit.

## The decision

- **Permissions: only what the app uses.** X11 and IPC for the windows, as JavaFX has no Wayland backend and so draws through XWayland on a Wayland desktop (`--socket=x11`, not `fallback-x11`, which would take X11 away there); the graphics card for its OpenGL drawing; the network for the forecasts; and on the session bus the panel's `org.kde.StatusNotifierWatcher`, `org.freedesktop.Notifications` and the Secret Service `org.freedesktop.secrets`. No file system access beyond the app's own folders, no other bus names. The manifest gives the reason of each, and `FlatpakPackagingTest` fails on any other.
- **The tray icon owns no bus name.** Outside the sandbox the item owns `org.kde.StatusNotifierItem-<process id>-1`. In the sandbox it registers with the panel by its connection's unique name, which KDE Plasma's and GNOME's AppIndicator watchers accept: so it needs no `--own-name`, and it cannot clash with another sandboxed app, whose process id is as low as its own.
- **Start at login through the Background portal.** The sandbox cannot write `~/.config/autostart`, so the app asks `org.freedesktop.portal.Background` (`RequestBackground` with `autostart` and the command line `car-charge-planner --background`), and waits for the portal's answer, which may ask the owner first. A refusal, a cancelled question, no portal or no answer within two minutes is an error the app shows as for any other failure to switch start at login.
- **"Is it on?" is the app's own memory.** The portal cannot be asked whether the entry is there. The app keeps a file, `car-charge-planner/start-at-login` in its config folder, while start at login is on, written only after the portal granted it and removed after it switched it off. Removing the entry in the desktop's own settings is not seen; switching it again in the app sets it right. Keeping it in `app.json` was the other choice, but would tie the app settings, which the owner edits and which hold no system state, to a platform part.
- **A shared runtime folder.** Flatpak gives each run its own `$XDG_RUNTIME_DIR`, so a second start would not find the running app's socket, and the panel and the notification server could not read the app's icons there. In the sandbox the app uses `$XDG_RUNTIME_DIR/app/<app ID>` instead, which every run of the app and the desktop share at the same path.
- **The menu entry and the notifications.** The Flatpak installs its menu entry as `<app ID>.desktop`, so `install-launcher` and `uninstall-launcher` say so and do nothing (the sandbox cannot reach the user's own entries anyway), and the notifications' `desktop-entry` hint is the app ID.
- **The keychain stays the same.** Its entries keep the attribute `application=car-charge-planner`, so API keys saved by the tar.gz or a package are found by the Flatpak, and the other way round.
- **A build from source, offline.** flatpak-builder brings the Maven of the wrapper, JavaFX's jmods from the address the other packages use, and every Maven file the build needs from `maven-sources.json`, each with its SHA-256; `tools/package-flatpak.sh` builds the same app image as `tools/package-linux.sh` and installs it in `/app`. `tools/flatpak-maven-sources.sh` makes the list by building once into an empty Maven repository, and only trusts a file whose SHA-1 is the one Maven Central publishes. JDK 25 comes from the `org.freedesktop.Sdk.Extension.openjdk25` extension of runtime 26.08; the app brings its own jlink runtime, as in the other packages, so the extension's JRE is not installed. For now only x86_64 (`flathub.json`), as the JavaFX jmods are per architecture.
- **The app ID is `io.github.enadeag.car_charge_planner.CarChargePlanner`:** Flathub's form for an app on GitHub, `io.github.<user>.<repository>.<name>` with the repository's dashes as underscores, which Flathub checks against the repository (the shorter `io.github.<user>.<repository>` cannot hold a repository name with dashes). An ID on an own domain would need that domain verified with Flathub; the maintainer chose the GitHub form for now. Flathub can move an app to a new ID later, but users then have to move along, so the ID is meant to stay. It is in as few places as possible; CONTRIBUTING.md lists them.

## Consequences

- The app's settings and data live in `~/.var/app/<app ID>/config/car-charge-planner` and `~/.var/app/<app ID>/data/car-charge-planner`, as the sandbox points `XDG_CONFIG_HOME` and `XDG_DATA_HOME` there; the app's code needs no change for it. Someone who moves from the tar.gz or a package copies `~/.config/car-charge-planner` and `~/.local/share/car-charge-planner` there, with the app quit; the API keys in the keychain carry over by themselves. The install guide says so once the app is on Flathub.
- Start at login has no state the app can read back, so a change made in the desktop's settings is not seen until it is switched again in the app.
- The release checklist has a `<release>` in the AppStream metadata for each release, which `FlatpakPackagingTest` checks against `CHANGELOG.md`, and a new `maven-sources.json` after each change to the Maven build.
- Until the Flatpak is built and tried in a sandbox on KDE Plasma and GNOME, this is untested on a real desktop.
