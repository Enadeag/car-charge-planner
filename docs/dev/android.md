# The Android app

The Android app ([ADR 0010](../adr/0010-android-app.md)) is built with Gradle in `android/`, apart from Maven. Gradle runs on a JDK 21 (`JAVA_HOME`); the engine is still compiled with `--release 17`. The build needs the Android SDK with platform 37 (`android-37.0` in the SDK manager, not a later 37.x) and build-tools 36.0.0, which Android Studio installs: name its folder in `sdk.dir` in `android/local.properties` (git ignores the file) or in `ANDROID_HOME`.

The Gradle wrapper checks the Gradle it downloads against `distributionSha256Sum` in `android/gradle/wrapper/gradle-wrapper.properties`. Every version the build uses is in `android/gradle/libs.versions.toml`, except the versions it shares with the Maven build (those of the engine's libraries and of PIT), which come from the parent `pom.xml` (see [Dependencies](ci-and-releasing.md#dependencies)). Plugins and libraries come only from Google's repository and Maven Central (`android/settings.gradle.kts`); the Gradle Plugin Portal is left out, so a plugin found only there brings it back in its own pull request, with the reason.

```bash
cd android && ./gradlew check assembleDebug    # build, lint and test; the APK is app/build/outputs/apk/debug/app-debug.apk
```

`check` runs the app's tests on the JVM, lint, and the build's own checks:

- `:engine` compiles `engine/src/main/java` as it is, and the contract tests `HttpGetContractTest`, `KeychainContractTest` and `FilePrivacyContractTest` from `engine/src/test/java`, by name, as test fixtures that the app's tests extend. They are compiled there, against the JDK, because `HttpGetContractTest`'s server is not in Android's API; the tests run on the JVM. A contract test that comes to need a helper gets it added to the list in `android/engine/build.gradle.kts`, and the build fails until it is. Its `checkMavenDrift` fails when the engine's libraries (Jackson and slf4j, and JUnit and AssertJ for the contract tests) are not the ones `engine/pom.xml` names; their versions come from the poms already.
- `:engine-lint` compiles the engine's sources once more, as an Android library that nothing uses, for two checks at the app's minimum, Android 10 (API 29), with the core library desugaring the engine needs (without it lint fails on `Stream.toList`, `URLEncoder.encode` with a `Charset` and `Duration.toSeconds`, `toSecondsPart` and `toNanosPart`). Lint skips `NewApi` in a plain Java module, hence this library.
  - Lint's `NewApi` covers the classes and methods that some Android version has: one that Android 10 lacks and desugaring does not add, such as `java.time.InstantSource`, fails the build.
  - `checkAndroidApiClasses` covers the classes that no Android version has: it reads the compiled classes and fails on a `java.*` or `javax.*` class missing from the compileSdk's `android.jar`, such as `ProcessHandle`, naming each and the engine class that uses it. Desugaring adds no class that a program compiled against the JDK can name.
  - The module is compiled with `--release 17`: against Android's own JDK classes the compiler would refuse the calls that desugaring adds, such as `Files.readString`.
  - A method that no Android version has and desugaring does not add is seen by neither check: `EngineArchitectureTest` keeps out the larger gaps, such as `java.net.http`, and the emulator job's instrumented tests and the check on a phone before a release are the backstop. `check` runs none of the ArchUnit rules on the engine's classes, as `EngineArchitectureTest` runs in Maven, so a change to the engine needs `./mvnw verify` too.
- The icons in the screens are Material's, not drawings of its own: from `androidx.compose.material:material-icons-core` at the Compose BOM's version, and the few Settings' list needs that it lacks copied into `ui/settings/SettingsIcons.kt` from `material-icons-extended-android` 1.7.8 (the BOM's), which is not a dependency: the six files merged into one object, each icon built on first use, names and path data unchanged. Another icon from outside the core library is copied there the same way. Both stay under the Apache License 2.0, as `NOTICE` says, and its text is in `android/legal/apache-2.0.txt`, whose header names each library and file it covers. The app's own source files carry no licence header; a copied one keeps its header and is named in a `Copied:` block, which `checkLegalFiles` holds it to (see [Dependencies](ci-and-releasing.md#dependencies)).
- `checkLegalFiles`, in `:app`, holds `android/legal` to what the release build brings, and `licenceAssets` puts those files, with the repository's `NOTICE`, `LICENSE` and `ADDITIONAL-TERMS.md`, in the APK's assets (`licences/`, with an index), from which Settings' last row, Open source licences, shows them. It writes the same bytes on every machine (UTF-8, `\n` line endings, a fixed order, no timestamp), so the APK stays reproducible. `LicencesInTheApkTest` reads the debug APK, which `check` therefore builds.
- `checkNoGoogleLibraries`, in each module, fails when a configuration resolves to Play Services, Firebase or the Play libraries (the groups `com.google.android.gms`, `com.google.firebase` and `com.google.android.play`), which F-Droid does not allow.
- `android/build-logic/` holds these checks, with the tests that show they fail when they should. `android/maven-poms/` holds what reads the poms: the settings plugin that puts the Maven build's versions in the catalog, of the Android build and of `build-logic` alike, and the reader `checkMavenDrift` uses; it is a build of its own, as `build-logic` cannot fill its own catalog, and its tests are in `build-logic`.

## The app's unit tests

The app's own tests, in `app/src/test/`, run on the JVM in one task. Its logic, in plain Kotlin classes, is tested with JUnit 5 against the stubs of Android's classes that the Android Gradle plugin provides. Its screens are tested on Robolectric, in JUnit 4, which JUnit's vintage engine runs beside JUnit 5:

- Android 17 only (SDK 37, the SDK the app is compiled against; `src/test/resources/robolectric.properties`), with Espresso 3.7.0 in place of the 3.5.0 that Compose's test rule brings, which fails on Android 17. The exceptions: a test of the notification card's refusal runs on Android 16, as Robolectric answers Android 17's permission question itself, and `AndroidKeystoreKeysOnRobolectricTest` runs on Android 12L and 13 (SDK 32 and 33), either side of the version that decides what a Keystore failure means.
- With Android's own text and graphics (`graphicsMode=NATIVE`, so a text and a control are as tall as on a phone) and with the app's resources.
- On JDK 21 Robolectric's Android 17 needs `jdk.internal.access` opened (`app/build.gradle.kts`).

**Start-up and StrictMode**

- `AppOnRobolectricTest` starts the app as Android does: the Application the manifest names (`CarChargePlannerApp`), which builds the engine, not started (the work in the background makes its rounds), the saves and the notification channels; and the activity, which opens on set-up when there is no settings file.
- StrictMode is on in the debug build only. A real disk read and a real disk write (opening a file for writing is a read and then a write, each its own crash) from the test's own frames crash the app on the main looper's next message, with the violation as the cause. StrictMode logs nothing itself. The debug build's policy equals a literal one of disk reads, disk writes and network only; the release build sets no policy (`applyMainThreadPolicy` with `debug = false` sets none).
- `OwnCodeTest` checks which stacks are the app's own (any frame in a package under `nl.enadeag.carchargeplanner.`, not a look-alike or the application ID). `MainThreadViolationsTest` checks that a violation of the app's own code crashes the app and one of a vendor's alone is a warning, once per kind and stack, up to a fixed number, after which one line says that no more are logged.

**Network, logging, keychain and platform**

- `AndroidHttpGetTest` holds `AndroidHttpGet`, the app's `HttpGet` on `HttpURLConnection`, to `HttpGetContractTest` on the JVM's `HttpURLConnection`. `LogcatLoggingTest` checks how slf4j's records become Logcat lines, with a sink that keeps them. As the Android stub fails when it is called, slf4j in these tests uses its no-op provider (`slf4j.provider` in `app/build.gradle.kts`), so the engine's records go nowhere there.
- `NetworkSecurityConfigTest` checks that the release build's network security config refuses plain http everywhere.
- `EncryptedKeychainContractTest` holds `EncryptedKeychain`, the app's keychain, to `KeychainContractTest`, with keys the JVM makes (`SoftwareKeys`) in place of the Android Keystore's, behind the store's seam for its keys (`KeychainKeys`): the file, its format, the encryption and what each failure means are the same code as on the phone.
- `EncryptedKeychainTest` checks how it encrypts and which failures it refuses as lost for good (a key still missing after a few looks, an entry that fails its check) and which it reports as unavailable (a file it cannot read, a Keystore that fails for now), as without the fallback to `secrets.json` a refused `index` starts a new one. It checks that the keychain never removes a key or an entry: a lost key is followed by a new one under a new alias, and an old key that comes back still opens its entries.
- `AndroidKeystoreKeysTest` checks which Keystore failures count as lost for good on the JVM, and `AndroidKeystoreKeysOnRobolectricTest` does so with Android's own Keystore exceptions on Android 12L and 13, as the answer changes at Android 13.
- `AndroidPlatformTest` checks the parts the app hands the engine: the API keys only in `keychain.json` in the folder that is never backed up, never in a file of their own, and the engine's files in the app's files folder. `DataExtractionRulesTest` reads the backup rules, which keep only the keychain's file, the notifications' state store and WorkManager's database on the phone.
- `AppEngineTest` builds the engine as the app does and reads `docs/example-engine.json` through it from the files folder (the file is a declared input of the test task, so a change to it runs the test again), and checks that the app offers the desktop's providers in the desktop's order. `EngineOnDispatcherTest` checks that each read and write of `EngineAccess` runs on the dispatcher it is given, and what the start sees for no settings file, a damaged one, one of a newer version and a usable one.

**`AppArchitectureTest`** holds the app's main code, Java and Kotlin, to ArchUnit rules, as `EngineArchitectureTest` does the engine. Each rule has a test with a class that breaks it.

- The screens draw their buttons with `AppButton`, `AppOutlinedButton` and `AppTextButton` (`ui/components/Buttons.kt`, the one file that calls Material's own), at least 48 dp high, never with Material's own, which are 40 dp.
- Only `AndroidHttpGet` opens network connections (no `URLConnection`, socket, OkHttp, WebView, `DownloadManager` or `java.net.http` elsewhere).
- No class sets up TLS of its own (a trust manager, a host name verifier, `SSLContext.init`, a security provider or property) or changes every connection of the process (a default proxy selector, authenticator or cookie handler, `HttpURLConnection.setFollowRedirects`, a system property or the live set `System.getProperties` hands out, as ArchUnit cannot read which one), as the engine's and the desktop's rules have it too.
- Only `LogcatSink` uses `android.util.Log`, while nothing writes to `System.out` or `System.err`.
- No class but the Application (`CarChargePlannerApp`), the parts it builds the engine with (`AppEngine` and `AndroidPlatform`), `EngineOnDispatcher` and the platform's keychain and log (the `secrets` and `logging` packages) uses the engine, the API keys, the keychain or the settings file itself: the screens and their logic use `EngineAccess`, which runs them off the main thread.
- No class outside the app's own `background` package (`nl.enadeag.carchargeplanner.android.background` and the packages inside it, not any package with a `background` part) calls `EngineAccess.round` or `nextNoticeDue` (through the interface or a class that has it; only a suspend function's own continuation may call it again), as a round tells the owner what is due. Only `EngineOnDispatcher`'s own `round` and `nextNoticeDue`, in the lambda they run on its dispatcher, call `Engine.round` or `Engine.nextNoticeDue` themselves.
- ADR 0005's rules, ported: only the Application, `CarChargePlannerApp` with the classes nested in it, reads the system's clock or time zone, and hands out the clock; only it, `AppEngine`, `AndroidPlatform` and `AndroidHttpGet` make a thread, an executor or a dispatcher of their own; no class keeps static mutable state (a static that is not final, or holds a mutable collection, an atomic, a builder, an array, a lock or a mutable flow; a Kotlin top-level `var` is one), apart from the resource IDs, the Compose compiler's lambdas and the keychain's lock per file, named in the rule.
- Only the keychain (`secrets`) writes, moves or deletes a file, as the engine writes its own through `PrivateFiles` and the phone's preferences go through DataStore.
- A class that makes or reads a request's address logs nothing.
- The logic, the store, the work in the background and the platform's parts know no screen (the `ui` packages); the app's packages have no cycles; and only the root package knows the Application, while the worker and the receivers find their parts through `BackgroundHost`, which the Application is.
- In the tests, only `Waiting` calls `Thread.sleep`: its `waitUntil` polls for a condition, and its `pause` gives another thread time to do the wrong thing.

**The work in the background** (`background`)

- JUnit 5, against an `EngineAccess`, an alarm and a work in memory, tests its rules (`BackgroundRules`: the alarm never within 9 minutes, its backoff after rounds without an outlook, what a start does, the network), its rounds (`BackgroundRounds`, under one lock that the Application hands to it and to the schedule), its schedule (`BackgroundSchedule`) and the `EngineAccess` that tells it of a saved change (`ReschedulingAccess`).
- On Robolectric, with WorkManager's `work-testing` and Robolectric's alarm manager: `AndroidNoticeAlarmTest` checks the alarm's kind, time, intent and replacement; `WorkManagerRoundsTest` the work's period, flex, names, network and lack of a battery condition, and the round now asked while one waits or runs and after a switch of "Wi-Fi only"; `BackgroundReceiversTest` the alarm's and the boot receiver; `BackgroundLifecycleTest` the activity's start, the saves and the "Wi-Fi only" switch; `RoundWorkerTest` the worker, with one real round of the app's engine on a fixed clock and a stored forecast that ends in a posted notice.
- Doze and the standby buckets are only in the instrumented `NoticeAlarmInDozeOnTheDeviceTest`.

**The screens** (the `ui` packages) are tested on Robolectric against the same `EngineAccess` in memory:

- Every step of set-up and every page of Settings in English and in Dutch, with no English text left on a Dutch screen.
- At twice the font size: every control with a name and a role, drawn at least 48 dp in both directions (its own size: Compose widens the touch area of anything clickable to 48 dp, so that is not checked) and reached by scrolling; and every page with room of its own scrolling far enough to show its last control whole. This is `ScreenChecks`, whose `ScreenChecksTest` shows that a control Material draws at 40 dp fails.
- The same names and sizes at the normal font size, once for each kind of screen (a set-up step, the list and a page of Settings, the dashboard with a plan and without one, the screen of an unusable file, a dialog), as a larger font hides a button drawn too small.
- Only the last field of a page has the keyboard's Done, the others Next; the focus is on a new step's heading or page's title and on the first problem.
- The Forecast page's window allows no screenshot and no autofill only while it shows, also after turning the phone or the system ending the app.
- What survives turning the phone and the system ending the app (`StateRestorationTester`); the engine's English details are marked as English.
- The dashboard's page of a day, which may end without a control, scrolls far enough to show its footer whole (`assertScrollsToShow`), also on a small phone on its side at twice the font size.
- `AppThemeTest` checks the wallpaper's colours from Android 12 on and Material's fixed ones before. `SourceColoursTest` checks that each energy source's text reaches 4.5:1 on its container in light and in dark, and that the charts' words reach 4.5:1 and their lines and marks 3:1 on their fixed ground.
- The solar chart and the battery bar are drawn with Compose's `Canvas`. Where their parts go (`ChartGeometry.kt`: the plot, the curve, which hours the time axis marks, the bar's marks) is plain Kotlin, tested with JUnit 5 with label widths given, at a dp of 1 and of 3 so that every size in dp is checked to grow with it. So is the draw list, which `SolarDrawing` and `BatteryBarLayout` make from the chart and the levels: the `Shape`s (`Line`, `Rect`, `Area`) in the order they are drawn, each with the `ChartInk` that names its colour (the grid, the charge windows' bands and marks, the solar area and curve, the house's dashed line and "now" on the chart; the track and its outline, the level after charging, the level, the line between them and the marks on the bar).
- `DrawnShapesTest` replays shapes through the real `drawn` modifier with pixel probes (an outline, a dash, a round cap, a corner, a closed area). The screen's tests check, through a test-only semantics property (`AxisLabels`), that the axis marks fewer hours at twice the font size, that right to left changes nothing in the chart's picture, and, with a pixel probe, that the cards stand on their fixed ground; each is checked to be one part with its sentence (`assertReadAsOne`).
- `MainActivityTest` starts the activity with an `EngineAccess` in memory and checks that a change of the app's language, which makes the activity again but keeps its view model, reaches the numbers the forms write and the place search, with what was typed kept.
- Compose's own accessibility checks find nothing on Robolectric, so they are not used.

**The logic of set-up, Settings, the home and which screen shows** (the packages `form`, `setup`, `settings`, `home`, `start` and `store`) is tested with `kotlinx-coroutines-test`, against an `EngineAccess` in memory, and with a `SavedStateHandle` carried over as Android does after it ended the app, which shows what survives: the texts, the step and which values are typical (no field shows it, but set-up and Save follow it), never an API key. `SunnyDayPlan`, the made-up sunny day the engine plans in `SunnyDayPlanTest`, is in `src/sharedTest/kotlin/`, which the JVM tests and the instrumented tests share.

`StringsResourcesTest` holds the Dutch texts to the English ones as the desktop's `MessagesBundleTest` does its languages (the same names, plural quantities and placeholders, all positional, nothing wrongly escaped), and checks that the languages the app offers are English and the `values-*` folders; Lint fails the build on the same kinds of mistakes (see [docs/translating-android.md](../translating-android.md)).

## The instrumented tests

The instrumented tests, in `app/src/androidTest/`, run on a device or an emulator with AndroidX Test, which is in their test APK only, never in the app:

- `OnTheDeviceTest` starts the app and has the engine plan the made-up sunny day on the device, through a `java.time` method that desugaring adds.
- `HttpOnTheDeviceTest` checks what Android's own `HttpURLConnection`, built on OkHttp, could do differently from the JVM's (compression, a connection that ends too soon, redirects, a repeated header, the network security config), against a small server on the device's loopback address.
- `LoggingOnTheDeviceTest` checks that slf4j finds the app's provider and a record reaches Logcat.
- `KeystoreOnTheDeviceTest` runs the keychain on keys of its own in the real Android Keystore (made at the first write, AES-256 for GCM, not readable out, no owner needed to use it, randomized encryption) and checks that a changed entry and a lost key give `REFUSED` and that a lost key is followed by one under a new alias.
- `AndroidPlatformOnTheDeviceTest` checks that the app has one set of platform parts, in its files folder and its folder that is never backed up.
- `ExampleSettingsOnTheDeviceTest` reads `docs/example-engine.json`, which the build puts in the test APK's assets, through the engine on the device.
- `KeysNotInLogcatOnTheDeviceTest` stores, reads and loses a made-up API key and checks that the app's own Logcat lines never hold it, as the emulator job publishes them.
- `NoticeAlarmInDozeOnTheDeviceTest` sets the app's real alarm about ten seconds ahead with the device forced into Doze (`dumpsys deviceidle force-idle`) and the app in the rare standby bucket, and checks that the notice shows. API 29 does not have the alarm limits of Android 12 and later; the check on a real phone covers those.

The device tests use a Keystore alias of their own, never the app's. The app refuses plain http, except in the debug build, to `localhost` and `127.0.0.1` only, for that server (`src/debug/res/xml/network_security_config.xml`). `./gradlew assembleDebugAndroidTest` builds their APK, and `./gradlew connectedDebugAndroidTest` runs them on the emulator or phone that `adb` sees.

## CI for the app

CI builds the app with `android.yml`, on Linux with JDK 21, in two jobs; [What is tested where](testing.md#what-is-tested-where) says when each runs and what it keeps. The emulator job uses an Android 10 (API 29) AOSP image without Google's apps. It makes a new AVD and boots it cold every run, without a cache or snapshot, as boots from the cached snapshot came up without the `input` service. Its emulator step has a 15-minute timeout, so a hang on shutdown (seen only on snapshot boots) fails the job fast instead of running into its 30 minutes. A change to `android.yml` runs the emulator job too, so it is tried before it is merged. Neither job is a required check yet: look at them before merging, until the maintainer makes them required once they run stably.

## Trying the app

Open `android/` in Android Studio and run the app on an emulator from its Device Manager (any system image from API 29) or on a phone; or start an emulator and run `adb install app/build/outputs/apk/debug/app-debug.apk` from `android/`. It opens on set-up, and after Finish on the dashboard, a tab per day of the plan, with Refresh and Settings in its top app bar.

The debug build crashes at once on a disk read or write or a network call on the main thread from the app's or the engine's code (StrictMode), so such a call is found while developing; one from the system's or a vendor's code alone, such as a phone's input code that reads a file on the first key, is logged as a warning, once. A call counts as the app's own when any frame of its stack is in a package under `nl.enadeag.carchargeplanner.`, so vendor code that runs inside one of the app's own lambdas still crashes the debug build.

The debug build has an id of its own, `io.github.enadeag.car_charge_planner.debug`, and a version name that ends in `-debug+<commit>` (the first 7 characters of the commit on CI: a pull request's head commit, or the pushed commit; `-debug+dev` on your machine), so it installs beside a release build, shows as "Car charge planner (debug)" in the launcher, and an APK signed with the public debug key can never update the released app.

To install the CI's build on a phone without a cable: open the pull request's `android-build` check, then its run (Details), and under Artifacts download `android-debug-apk-<run number>-<attempt>` while logged in to GitHub; unpack the zip, open `app-debug.apk` and allow installing from the browser or Files when Android asks; Play Protect may warn about an app it does not know. Only `app-debug.apk` is kept, for 14 days, and not for a pull request from a fork or from Dependabot; pushes, the weekly run and a run by hand keep it too.

Every debug build is signed with the same key, `android/app/debug.keystore` (password `android`, alias `androiddebugkey`): it is public and no secret, made for this project and no one's own, so a newer debug build updates an older one. Install a debug APK only from this repository's own runs; the debug app's data is only as safe as the public debug key, so keep real provider keys out of it or accept that.

Release signing is not set up yet (#271, #272). `checkReleaseNotDebugSigned`, in `check` and before every build of a build type other than debug, fails when such a build type, with the signing config it ends up with (its own, a product flavor's or the default config's), is signed with the debug key.
