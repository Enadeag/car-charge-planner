# Security policy

## Reporting a problem

Please report a security problem privately, not as a public issue: open the repository's **Security** tab and choose **Report a vulnerability** (GitHub private reporting). Say what you found, how to reproduce it, and which version.

You will get an answer within a week or so. This is a small project run by one person, so there is no bug bounty and no fixed fix time, but a confirmed problem is fixed in the next release and credited if you wish.

## What matters here

The app runs on your own computer and only talks to the forecast provider you chose. Things worth reporting: a way to read or overwrite files outside the app's own folders, a forecast provider's API key shown or stored where other users can read it (`secrets.json`, used where there is no system keychain, must be readable by you alone), or a crash that a forecast response can trigger.

On Android the same holds for the phone app: an API key that leaves the encrypted keychain or reaches Logcat, another app reaching a component the app does not export or the app's own files, or a crash that a forecast response can trigger.

## Accepted risks

These are known and deliberately left as they are; a report that shows they matter more than described here is welcome.

- **Linux: the API keys cross the session bus unencrypted.** The app asks the Secret Service (GNOME Keyring, KWallet) for the API keys in a "plain" session, not an encrypted one. The API keys travel over your own session bus, which only programs running as you can use, and such a program can ask the Secret Service for them just as well; encrypting the session would not keep it out.
- **Linux: other programs in your session can use the tray icon.** The tray icon is a StatusNotifierItem on your session bus, so any program running as you can read its tooltip (the plan's state) and choose its menu entries: open the dashboard, Settings or About, or quit the app. It cannot change a setting or read an API key that way. Only programs running as you can reach your session bus.
- **The single-instance folder is checked one level up.** Before the app makes its private folder for the lock file and socket owner-only, it checks the folder itself (yours, not a link, not writable by others, no files of other users and no hard links) and its parent (yours or root's, not a link, not writable by others), and checks again after the change that it is still the same folder. It does not check every folder above it or the whole contents: the folder lives in your own `XDG_RUNTIME_DIR` or `~/.local/share`, and whoever can write in the folders above those already controls your account.
- **Android: the Keystore key is usable while the phone is locked, and is not in StrongBox.** The background rounds need the API keys with the screen off, so the key that encrypts them does not require an unlocked phone, and it lives in the Android Keystore without the StrongBox hardware. Another app cannot read it; someone with root on the phone, or code that controls its system, can use it, also while the phone is locked.
- **Android: the settings move to your next phone.** The settings file, with the home's coordinates, the trips and the app's other files named in its backup rules travel in Android's device-to-device transfer. The API keys are kept out of it and must be typed again on the new phone, and there is no cloud backup on any version. On Android 10 and 11 the rules let a file go only into a backup whose transport says it is a transfer between two devices, a flag Android leaves to the phone's maker: a maker's own backup that sets that flag wrongly, or ignores it, could take the settings and the trips to wherever it keeps its backups. The API keys never go: they are in the no-backup folder, which Android never takes along, and their Keystore key cannot leave the phone. Also accepted: with backup on, `adb restore` on Android 10 and 11 can put the seven listed files into the released app, since a restore checks the list and not the flag; it needs the owner's unlocked phone with USB debugging on and a tap on the phone to confirm, it wipes the app's data and its stored keys first, and it gives that person nothing that Settings does not, such as a server address of their own for Open-Meteo, which would then receive the home's coordinates and a key typed again (#397).
- **Android: the debug APK is signed with a public key.** The debug build that CI attaches to a run uses a debug keystore that is in the repository. Anyone can sign an APK with it, so the debug build is for trying and testing only and its data is only as safe as that key. Keep real provider keys out of the debug build, or accept that risk. A released APK, from the repository's GitHub Releases, is signed with the release key, whose certificate's SHA-256 fingerprint is in `android/release-certificate.sha256` and in its release notes.
- **Android: a release can be rebuilt from its tag.** Each release is built twice on GitHub's runners and is signed only when both unsigned APKs are identical, so an APK built from the tag with the Java, platform and build-tools of that release should match it apart from the signature, which can be copied onto it. A matching rebuild shows what the release was built from, not that the code, the runner or the tools can be trusted. F-Droid's buildserver image, with Debian's OpenJDK 21 instead of the release's Temurin, built 0.2.0's unsigned APK byte for byte, and fdroidserver copied the released signature onto it and verified it ([Reproducible build](docs/design/android/build.md#reproducible-build)).
- **Android: the build's checksums are trusted from their first download.** The Android build checks every library and plugin it downloads against a SHA-256 recorded in the repository (`android/gradle/verification-metadata.xml`) and stops on any other file, so a file changed after it was recorded, in a repository or in a cache, stops the build. The checksums are recorded by `tools/refresh-android-verification.sh`, which downloads every file afresh from Google's Maven repository and Maven Central when a dependency is added or updated, so a file that was already wrong there at that moment is not caught; and as a pull request can change a dependency and its checksum together, the file's diff is read before the merge. The check says nothing about known vulnerabilities in a library, and does not cover the Gradle distribution (checked by its own SHA-256), the Android SDK and build-tools, or the JDK that builds the app ([Dependency verification](docs/dev/android.md#dependency-verification)).

## Supported versions

Only the latest release of each app.
